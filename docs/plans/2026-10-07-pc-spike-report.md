## 2. 硬解自证（验收 2 / 4 / 5）

**判据**（方案 §3.3B 的 ★）：逐路首帧 `AVFrame.hw_frames_ctx != null` **且**
`AVFrame.format == AV_PIX_FMT_D3D11`。

**绝不软解是**用 `get_format` 回调**强制**的：回调只接受 `AV_PIX_FMT_D3D11`，找不到就返回
`AV_PIX_FMT_NONE` ⇒ `avcodec_open2` 直接失败 ⇒ 「拿不到硬解」变成**明确的打开失败**，
而不是 FFmpeg 默认的**静默回落软解**。

| 独立旁证 | 结果 |
|---|---|
| `nvidia-smi pmon` 的 `dec` 列（硬解引擎占用） | 单路 11% → 16 路 81% → 32 路 81% ⇒ **引擎确实在工作** |
| 实测落到软解的路数 | **0**（含 32 路并发） |

### 2.1 硬解设备（验收 5）

| 设备 | `av_hwdevice_ctx_create` |
|---|---|
| `d3d11va` · `dxva2` · `d3d12va` · `cuda` · `vulkan` · `opencl` | ✅ 可创建 |
| `vaapi` · `qsv` · `amf` | ❌ 失败（本机无对应厂商设备） |

> 「编译进来」≠「本机能用」—— 所以逐个**实试创建**，不只看枚举（探测给候选，试错给结论）。

### 2.2 纵向超长尺寸（验收 4 —— 原最大风险项）

| 样片 | 结论 | 首帧回读 |
|---|---|---|
| **1440×3200 H.264 High** | ✅ **硬解成立** | 6.0–9.5 ms |
| **1440×3200 HEVC Main** | ✅ **硬解成立** | 5.8 ms |

⇒ **1440×3200 纵向超长不构成限制，不约束 agent 侧的编码参数与虚拟屏尺寸选择** ✓

## 3. 帧通路成本（验收 3，T1 路径）

`硬解 → av_hwframe_transfer_data 回读 NV12 → 两个平面纹理（R8 + Rg8）→ 着色器转 RGB → egui 上屏`

| 分辨率 | 回读 P50/P95 | 上传 + 转 RGB | 单路 CPU（单核 %） |
|---|---|---|---|
| 1280×720 | 2.1 / 2.5 ms | — | — |
| 1920×1080 | 4.1 / 4.3 ms | 0.6 ms | **45.4 %** |
| 1440×3200 | 9.5 / 10.9 ms | 1.3 ms | **86.0 %** |

> **T1 可行** ✓ —— 回读 + 上传的固定成本在 60fps 预算（16.7 ms）之内。

### 3.1 CPU 分解（**决定 T1 是否够用的关键**）

单路那个 45–86% 会误导：它含窗口/呈现等一次性与固定项。逐档加路（1080p60，缓冲 2 帧，全部循环播放）：

| 路数 | CPU（单核 %） | 每路 |
|---|---|---|
| 0（只有窗口） | **0.3** | — |
| 1 | ~48 | 48 ⚠️ |
| 2 | 52.4 | 26.2 |
| 4 | 113.3 | 28.3 |
| 8 | 197.4 | 24.7 |

⇒ **边际成本 ≈ 25–28 单核 %/路 @1080p60**（2→8 路拟合：(197.4−52.4)/6 = **24.2**）。

> ⚠️ **1 路那格（48%）与 2 路（52.4%）不成比例，未解释** —— 只记录测量值，
> 不编造归因。可决策的是**边际成本**那一列。

**结论（T1 vs T0）**：本机 24 逻辑核 ⇒ CPU 侧可支撑 `24 / 0.25 ≈ **96 路**`，
而 GPU 解码引擎实测上限是 **8 路** ⇒ **CPU 余量约 12×，瓶颈是 GPU 而不是 CPU**。
1440×3200 同向（86 单核 %/路 vs GPU 上限 4 路 ⇒ 余量约 7×）。

⇒ **T1 的 CPU 成本不构成瓶颈，不需要 T0（零拷贝）** ✓

## 3b. 裸 Annex-B 路径（**真实链路走的就是这条**）

spike 前期的样片是 **mp4**（有容器）；而 F4 送过来的是**裸 Annex-B 码流**（无容器、无 CSD 交换）。
两者是**不同的解复用路径**，所以单独验：

| 用例 | 结果 | readback | `lat` |
|---|---|---|---|
| 1920×1080 H.264 裸流 | ✅ `hw_frames_ctx=set` | 2.4/3.3 ms | **9.2/9.6 ms** |
| 1440×3200 H.264 裸流 | ✅ | 6.2 ms | — |
| 1440×3200 HEVC 裸流 | ✅ | 5.1 ms | — |
| 1920×1080 H.264 裸流 · **中途切入**（无前置参数集） | ✅ | 2.3/2.9 ms | **9.3/9.7 ms** |

**三条结论**：

1. **裸 Annex-B 硬解成立** ✓ —— 强制 `h264` / `hevc` 裸解复用器即可（`avformat_open_input` 猜不出格式）。
2. **中途切入成立** ✓ —— 从第 2 个 IDR 起、前面不带任何参数集也能解
   ⇒ 印证了 agent 侧 `PREPEND_HEADER_TO_SYNC_FRAMES = 1`「**每个 IDR 自带参数集**」的结论 ✓
3. ⚠️ **裸流完全没有 PTS**（mp4 有 `256/512/768…` @1/15360；裸流全是 `N/A`），
   且 FFmpeg 对裸流猜的帧率**是错的**（`r_frame_rate=120/1`、`avg_frame_rate=25/1`，真实 60）✗
   ⇒ **PC 不得从裸解复用器推导帧率**，必须用握手协商来的参数。

### 3b.1 「无时间戳」= 直播语义

裸流没有源时间轴 ⇒ spike 把它建模成**直播模式**：**不做时间轴节流，到达即上屏**
（真实链路本来就是实时流，到达速率就是编码器的速率）。

**这改变了延迟的构成**：

| 模式 | `lat` P50 | 说明 |
|---|---|---|
| 文件回放（有 PTS，节流） | 38.6 ms @缓冲 2 帧 | 延迟由**缓冲深度**主导（§4） |
| **直播（无 PTS，不节流）** | **9.2 ms** | 延迟 = **流水线成本本身**；缓冲只作**抖动吸收**，不再主导延迟 |

⇒ **产品（远程操控）走的是直播语义** ⇒ 缓冲的作用从"延迟旋钮"变成"抖动吸收器"，
应当**按预期网络抖动来定**，而不是按延迟预算反推。

## 4. 端到端延迟（验收 8）

**两个口径必须分开**（否则会得出矛盾结论）：

- **`lat`（播放侧延迟）**：回读完成 → 提交上屏。**含缓冲排队**，是产品延迟的主要来源。
- **`e2e`（时间轴对齐）**：源时间轴应上屏时刻 → 实际上屏时刻。只说明"上屏是否按点"，**不代表低延迟**。

### 4.1 缓冲深度是延迟的主导项（1080p60，单路）

| 缓冲帧数 | `lat` P50 | `lat` P95 | `e2e` P50 | fps | drop |
|---|---|---|---|---|---|
| **2**（**下限**） | **38.6** | 45.6 | 3.0 | 59.9 ✓ | 0 |
| 3 | 56.1 | 58.0 | 3.1 | 59.9 ✓ | 0 |
| 4 | 74.4 | 76.2 | 3.0 | 60.3 ✓ | 0 |
| 5 | 88.6 | 94.3 | 3.4 | 60.3 ✓ | 0 |
| 6 | 105.1 | 111.8 | 3.0 | 59.9 ✓ | 0 |
| 12 | 207.8 | 209.5 | 2.7 | 60.0 ✓ | 0 |

> 缓冲 1 帧在实现上不可达（通道与展示队列各至少 1 帧）⇒ **2 帧是本 spike 的结构下限**。

**斜率 = 16.8 ms/帧 ≈ 1/60 s** ⇒ 模型成立：

```
lat ≈ 缓冲帧数 × 帧间隔 + 链路固定成本（回读 + 上传 ≈ 5 ms @1080p）
```

**分辨率无关**（缓冲 3 帧）：720p **58.3** / 1080p **56.5** / 1440×3200 **51.0** ms ✓

### 4.2 结论

1. **缓冲深度是延迟旋钮**，必须按目标延迟反推，**不能按"越大越稳"定** —— 12 帧就是 208 ms。
2. **实测下限 2 帧 = 38.6 ms**（本 spike 的结构下限：通道与展示队列各至少 1 帧）。
   ⚠️ 早期测出的"2 帧饿死"**不是本质约束，是漏唤醒 bug** —— 见 §8「显示后队列空不排重绘」。
3. 回读 + 上传的**固定成本只有 ~5 ms**（1080p）；延迟的其余部分全是缓冲。
4. **本应用是远程操控 ⇒ 缓冲应取尽可能小**（延迟优先于抗抖动）——
   取 2 帧即 **38.6 ms**，比 6 帧（105 ms）少 **66 ms**。

## 5. 并发与吞吐（验收 6 —— **事实记录**）

> ⚠️ 用户已决定**不做容量处理**。本节只记录实测事实，**不含任何容量管理设计**。

| 分辨率 | 可持续 60fps 路数 | 越界后的表现 |
|---|---|---|
| 1920×1080 | **8 路**（每路 60.0 fps，drop 0） | 12 路 → 44.2 fps；16 路 → 32.0 fps |
| 1440×3200 | **4 路**（每路 60.0 fps，drop 0） | 6 路 → 57.3 fps |

两个分辨率独立收敛到同一吞吐 **≈ 1.0–1.1 Gpixel/s**（8×60×2.07M = 0.995；4×60×4.61M = 1.106）。

**关键事实：加路从不"失败"。** 一路加到 32 路（1080p）全部准入成功、**全部 `hw-verified`**、
无一路软解、无参数被改 —— 只是每路的 fps 按比例下降。**系统是优雅劣化，不是硬失败。**

### 5.1 资源占用

| 场景 | CPU（单核 %） | GPU SM / dec | 显存 | 私有内存 |
|---|---|---|---|---|
| 1×1080p60 | 45.4 | 23 / 11 | — | 559 MB |
| 16×1080p60（32 fps） | 224.5 | 34 / **81** | 3187 MiB | 3412 MB |
| 32×1080p60（32 fps） | 224.5 | 34 / **81** | — | 3412 MB |
| 1×1440×3200@60 | 86.0 | 49 / 27 | — | 676 MB |
| 6×1440×3200（57 fps） | 234.2 | 17 / 70 | 3034 MiB | 1942 MB |

### 5.2 多路 × **最小缓冲**（缓冲 2 帧）

缓冲取最小是否还能多路稳定？实测（每路 60fps 目标）：

| 配置 | 每路 fps | `lat` P50 | drop |
|---|---|---|---|
| **8 × 1920×1080** H.264 | 59.9–60.4 | 35.5–38.8 ms | 0–3 |
| **4 × 1440×3200** H.264 | 59.9–60.3 | 32.0–34.8 ms | 0–3 |
| **4 × 1440×3200** HEVC | 59.6–60.4 | 32.5–36.5 ms | 0–3 |

⇒ **最小缓冲在多路下同样稳定** ✓ 且 `lat` 不比单路差（多路时甚至略低）。
`drop 3` 是**循环重开样片**的一次性抖动（约 40 秒 3 帧），不是稳态丢帧。

### 5.3 验收 7（失败行为）

**方案 §3.3E 要求提供故障注入开关** —— 否则回收与回滚代码**永远不会被执行**，等于没写。
实测两条路径均按预期分类与回滚：

| 注入 | 结果 |
|---|---|
| `SPIKE_FAIL_OPEN=2` | `REJECTED #2 (decoder-open: 故障注入：强制建解码器失败)` |
| `SPIKE_FAIL_TIMEOUT=2` | `REJECTED #2 (first-frame-timeout)` |

两者都**不影响已在跑的 2 路**（继续 60fps）✓，且准入失败返回的是**带阶段**的原因
（`decoder-open` / `first-frame-timeout` / `not-hardware-frame` / `readback` / `texture` 五类分开）✓。

**「绝不软解」与「不悄悄改参数」**：全负载区间（1–32 路）内**没有一路落到软解**、
**没有一路的参数被改** —— 因为「绝不软解」是**结构性保证**（`get_format` 只接受 D3D11，
拿不到就 `avcodec_open2` 失败），不依赖运行期检查。

**「超容量时拒绝新增路」**：实测**不存在"超容量"这个状态** —— 加路从不失败，只有 fps 劣化（§5）。
用户已决定**不做容量处理**，故该条不再适用。

## 7. 复现方式

```bash
# 构建（四个环境变量见实施记录 §3.3）
cd pc && cargo build --release

# 单路播放（1080p，默认缓冲 6 帧）
target/release/spike.exe D:\wcreen-samples\t-1920x1080-h264.mp4 d3d11va

# 延迟标定：缓冲 3 帧（SPIKE_BUFFER=<总帧数>，通道至少 1 帧）
SPIKE_BUFFER=3 target/release/spike.exe D:\wcreen-samples\t-1920x1080-h264.mp4 d3d11va

# 并发（SPIKE_PROBE=<目标路数>，到文件尾会循环，保证持续有流）
SPIKE_PROBE=16 target/release/spike.exe D:\wcreen-samples\t-1920x1080-h264.mp4 d3d11va

# 故障注入（验证准入回滚路径）
SPIKE_PROBE=3 SPIKE_FAIL_OPEN=2    …    # → REJECTED #2 (decoder-open: 故障注入…)
SPIKE_PROBE=3 SPIKE_FAIL_TIMEOUT=2 …    # → REJECTED #2 (first-frame-timeout)
```

**证据留档**：程序每 10 秒把每路的 `fps / readback / lat / e2e / drop` 打到 stdout
（`STAT #…` 行）；准入结果打 `ADMITTED` / `REJECTED`（带**失败阶段**）。

## 8. 工程记录（期间修掉的缺陷）

| 缺陷 | 现象 | 根因 |
|---|---|---|
| **use-after-free** | 0xC0000005 硬崩 | `Pending::take()` 返回的临时值在函数末尾析构，把刚交出的 5 个 FFmpeg 句柄全释放了 |
| eframe/egui 0.36 API 迁移 | 编译失败 | `App::update(ctx)` → `App::ui(ui)`；`TopBottomPanel` → `Panel::bottom`；`CentralPanel::default()` → `no_frame()` |
| PTS 节流活锁 | 解码器跑到文件尾、画面不动 | "只留最新帧"使 `pending` 每次被推后 2 帧，`wait` 单调增长 ⇒ 永远追不上 |
| 播放停死 | 画完一帧后卡住 | 下一帧未到期时**没排重绘**，而解码线程正阻塞在满通道上 ⇒ 无人叫醒 UI |
| 稳态误丢帧 | `drop` 持续增长 | `MAX_LAG`(=100ms) 不大于总缓冲(6 帧=100ms) ⇒ 每帧都恰好"迟到" |
| 画面压成一条线 | 视频区只剩几像素宽 | `available_height()` 在 `horizontal_wrapped` 内部退化为 0 |
| **样片回归（自己引入并已修复）** | 丢失帧号水印 / 变成有限范围 / 时长变 60s | 曾按"真实投屏是有限范围"的推断重生成样片，**违背实施记录 §4 已定的参数**（全范围 + `drawtext` 帧号 + 10s）。已按 §4.2 原命令逐字节还原 |
| **漏唤醒死锁** | 缓冲 ≤2 帧时播放**偶发冻结**（`fps 0.0`，画面停住，`STAT` 也不再打） | `fill_queue` 在展示队列满时**不取通道**；显示完最后一帧后队列空 ⇒ 原来**不排重绘**，而解码线程正阻塞在 `send` 上（其唤醒标志在阻塞**之前**已用掉）⇒ 双方互等。修法：**显示后队列空必须立刻再排一次**。⚠️ 该 bug 曾把下限**误报为 3 帧**（真值 **2 帧 / 38.6 ms**） |
| 证据丢失 | `STAT` 行有时读不到 | stdout 被重定向时是**块缓冲**，进程被强杀会丢缓冲 ⇒ `note()` 里显式 `flush` |
| 生产者唤醒顺序 | 早期版本在 `send` **之后**才 `request_repaint` | `send` 可能阻塞 ⇒ 阻塞后没人叫醒 UI。修法：**先叫醒，再送**（顺序不能换） |
