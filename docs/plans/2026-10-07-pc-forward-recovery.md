# PC 侧：`adb forward` 丢失后的自愈与诊断

> 本文件是 [`docs/spec/workflow.md`](../spec/workflow.md) §2 定义的**实现方案文档**。
> 写完即冻结；实施中的偏差另建文档。范围只含 PC 侧，**不动 `:agent`**。

**状态**：**已批准**（2026-10-07，用户选定「自动修复 + 失败时明确诊断」）。

---

## 1. 背景与目标

**现象**（用户实测报告）：USB 掉线后重新连接设备，PC 侧**永远连不上**。

**实测根因**（2026-10-07）：

```
adb forward --list   →  （空）
127.0.0.1:27183      →  连不上（无监听 / 连接被拒）
设备本身              →  在线
```

`adb forward` 是**挂在 adb 传输连接上**的：USB 一掉、传输消失，转发被 adb 一并清掉，
插回来后**不会自动恢复** ✗。PC 侧连的是本地端口 `127.0.0.1:27183`，于是
`TcpStream::connect` 一直被拒 ⇒ 重连循环每秒重试一次、**永远失败**，
且没有任何一方负责补转发。

**附带现象**（**不在本片范围**）：断开时 agent 会把虚拟屏**释放**掉（S2 语义「断开即拆屏」），
所以重连后屏上的 App 也没了。「断开后**冻结**、重连**认领**」是 **S5** 的内容 ——
用户已确认**保持现状、留给 S5** ✓。

**目标（验收标准，可观测）**：

1. 转发缺失时，PC **自动**执行 `adb forward tcp:<port> localabstract:<name>` 并恢复连接 ——
   无需人工干预；
2. 自动修复**失败**时（设备离线 / 没装 adb / 名字写错），界面与日志给出**可诊断原因**
   与**可直接照抄的命令**；
3. 修复动作**限频**（≥5s 一次），不得在重连循环里每秒调一次 `adb`；
4. 不影响既有行为：转发本来就在时**不执行任何 adb 命令**（零额外开销、零风险）。

## 2. 现状调研（事实依据）

| 事实 | 依据 |
|---|---|
| 转发会随 USB 断开被清掉，且不自动恢复 | 上面实测（`adb forward --list` 为空、端口拒连、设备在线） |
| PC 只连本地端口，不知道转发是否存在 | `pc/app/src/conn.rs::connect`（`TcpStream::connect_timeout`） |
| 重连是「1s 退避、无限重试、不诊断」 | `pc/app/src/session.rs::reconnect` |
| 首连失败是**硬退出**（退出码 1） | `Session::start` → `main` |
| 已有的诊断范式可照抄 | `session.rs::handshake_failure`（把「端口转发还在、设备上没人在听」写透） |
| 转发的目标名已在部署文档里固定为 `localabstract:wcreen` | `agent/module.md` §5、`cli.rs` 帮助文本 |
| CLI 目前没有「抽象名」这个选项（只有 `--port`） | `pc/app/src/cli.rs` |

## 3. 方案与取舍

### 3.1 采纳：**连接被拒时自动补转发，失败则明确诊断**

| 环节 | 做法 |
|---|---|
| 触发条件 | `TcpStream::connect` 返回**连接被拒**（`ErrorKind::ConnectionRefused`）—— 这才是「本地端口没人在听」的确定信号，其它 IO 错误不触发 |
| 动作 | 执行 `adb forward tcp:<port> localabstract:<name>`（`--name` 新增，缺省 `wcreen`，与 agent 的 `--name` 同名） |
| 限频 | 会话线程内记 `last_repair: Instant`，**≥5s 才允许再次执行** |
| 成功 | 照常继续重连；日志记一条「转发缺失 ⇒ 已自动重建」 |
| 失败 | 把 `adb` 的 stderr + 两条最可能的原因（设备离线 / 未装 adb）+ **可照抄的命令**写进 `Status.message` 与日志 |

**为什么用「连接被拒」而不是「先无条件跑一次 adb」**：无条件跑会给每次启动都加一次进程创建，
且**掩盖**真正的错误（例如 agent 没起、名字写错）；只在确定信号下动手，代价与风险都最小。

### 3.2 被否方案

| 方案 | 否掉原因 |
|---|---|
| 只做诊断、人工补转发 | 用户已选自动修复；掉线重插是**常态**，每次都人工一步不可接受 |
| 独立脚本 `pc/scripts/forward.sh` | 仍需人工触发；且把「谁负责恢复」摊到了两个地方 |
| 不做连接被拒判断、每次重连都跑 `adb forward` | 每秒一次进程创建；且会把「设备离线」这类真实错误盖住 |
| 改用 `adb reverse` / 让 agent 监听 TCP 直连 | 都要改契约与部署方式，超出本片范围（网络侧属 §未决项） |

## 5. 实施步骤

1. 新增 `forward.rs`：`repair(port, name) -> Result<(), String>`（跑 `adb forward …`）与
   `diagnose(port, name, stderr) -> String`（拼可照抄的说明）；
2. `cli.rs` 加 `--name`（缺省 `wcreen`，与 agent 同名）并更新帮助；
3. `SessionConfig` 加 `name`，`main` 透传；
4. 把「连接被拒」从普通 IO 失败里分出来（`SessionError` 新增变体）；
5. `reconnect` 循环：遇到该变体 ⇒ 限频 ≥5s 调一次 `forward::repair` ⇒ 成功记日志、失败写诊断；
6. 首连失败同样先尝试一次修复，再给出诊断并退出（退出码 1）；
7. 单测：诊断文案的拼装（含/不含 stderr 两种）、`--name` 解析与缺省。

## 7. 风险与回滚

| 风险 | 应对 |
|---|---|
| 误判「被拒」为转发问题（其实是别的进程占了端口） | 诊断文案**并列**列出两种可能 + 给出 `adb forward --list` 与端口检查命令，不武断下结论 |
| 反复调 `adb` 造成负担 | 硬性 ≥5s 限频 + 只在「连接被拒」时触发 |
| 没有 `adb` 可执行文件 | `Command::new("adb")` 失败 ⇒ 直接走诊断分支，提示装 adb / 手动执行，不 panic |
| 回滚 | 改动集中在 3 个文件 + 1 个新文件；删掉修复调用即回到原行为 |
