# PC 端 spike 方案（egui + wgpu + FFmpeg 硬解）

> 状态：**已批准**（2026-10-07；按 [`AGENTS.md`](../../AGENTS.md) 的 workflow，批准后方可动代码）
> 依据：[`docs/spec/tech-stack/pc.md`](../spec/tech-stack/pc.md) §2「多路合流、硬解与帧通路」、§3「容量模型」
> 本文件批准后**长期保留**，实际偏差另建文档记录，不回头改本文件。

---

## 1. 背景与目标

技术栈已定（PC 端 Rust + egui + wgpu + FFmpeg，硬解，不做软解），但**三个关键假设没被验证过**：

1. FFmpeg 硬解出来的帧**能否与 wgpu 协作**（T1 路径）并且 CPU 开销可接受；
2. 平台硬解器的**容量**（并发实例数、最大尺寸）到底是多少 —— 技术栈规定容量「运行时动态决定」，
   而其中一半能力**查不到**，只能实测；
3. 手机原生尺寸（如 1440x3200 纵向超长）**是否超硬解器上限** —— 这直接决定 agent 侧要编什么。

本 spike 的唯一目的是**用实测数据回答这三个问题**，并同时验证 egui + wgpu 的最小渲染链路。
**它不产出产品功能。**

### 验收标准（可观测）

| # | 验收项 | 观测方式 |
|---|---|---|
| 1 | Windows 上出现 egui 窗口，播放硬解后的视频，画面正确 | 目视 + 与样片逐帧比对（可抽帧） |
| 2 | **确实是硬解**，不是软解 | **逐路首帧校验帧是硬件帧**：`frame->hw_frames_ctx != null` / `frame->format == AV_PIX_FMT_D3D11`。<br>CLI 等价判据：`-vf hwdownload,format=<nv12\|p010>` 返回 **rc=0**（该滤镜只对硬件帧生效）。<br>**⚠️ 不能以"没报错 / 退出码 0"为准** —— FFmpeg 对不支持的参数会**静默软解**（见 §2） |
| 3 | 帧数据走 **T1 路径**（回读 + GPU 转换），CPU 占用有数 | 1080p60 单路持续播放：进程 CPU 占用、内存、GPU 3D/Video 占用 |
| 4 | **1440x3200 纵向超长样片**给出明确结论 | 能硬解 → 记可用的解码器与参数；不能 → 记**我们自己产生的**错误（**不能等系统报错**，见 §2） |
| 5 | 产出本机**能力探测结果** | 硬解设备列表、每个解码器的 codec/profile 与**输出像素格式**；可上传的软件像素格式列表。**注意：分辨率范围没有 API**（d3d11va 下 `AVHWFramesConstraints` 不填尺寸字段），只能逐点实测 |
| 6 | 产出**实测容量曲线** | 逐路增加到失败：各分辨率下可持续路数与失败时的原始错误 |
| 7 | 超容量时**明确失败（拒绝新增路），不降级、绝不软解**；且区分「新增被拒」与「已在跑的路崩了」 | 观察进程行为 + 日志；用 §3.3E 的故障注入开关强制触发**回收路径**；确认没有软解回退、**没有参数被悄悄改** |
| 8 | 端到端延迟可量化 | 样片内嵌时间戳 / 已知帧序，量「解码完成 → 上屏」的耗时分布 |

## 2. 现状调研

| 事实 | 出处 |
|---|---|
| 本机 Rust 1.97.1 stable / `x86_64-pc-windows-msvc`，已装 `aarch64-linux-android` target | `rustc --version`、`rustup show` |
| 本机 ffmpeg 是**纯二进制包**（仅 `ffmpeg.exe` / `ffplay.exe` / `ffprobe.exe`），**无头文件与导入库**，不足以链接 | 检查 `Desktop/ffmpeg-9.0.2-essentials_build/bin` |
| `egui_wgpu::Renderer::register_native_texture(device, view, filter) -> TextureId` 与 `egui_wgpu::Callback` 是官方 API | docs.rs `egui-wgpu` |
| wgpu 导入外部纹理需 `unsafe`：`Device::create_texture_from_hal`、`hal::vulkan::Device::texture_from_raw`；且 `texture_from_dmabuf_fd` **不支持多平面 NV12 dma-buf** | docs.rs wgpu / wgpu-hal；gfx-rs/wgpu #9801、#10059、#6248 |
| 硬解器并发上限**无标准 API**，只能实测 | [`tech-stack/pc.md`](../spec/tech-stack/pc.md) §3「容量模型」 |
| **FFmpeg 对不支持的参数会静默软解，退出码仍为 0**（实测：H.264 4:4:4 / 10-bit、HEVC 4:4:4、MPEG-4 @1440x3200 全部静默软解；`GetVideoDecoderConfigCount` 报 0 的那个尺寸同样不报错） | 本机实测（判据：解出的帧格式 `d3d11` vs `yuv*`，以及 `hwdownload` 是否成功） |
| **wgpu 30 的 DX12 适配器与 D3D11 解码设备在同一适配器**（LUID 均为 `00000000:0000C992`）→ 跨适配器不是本机阻塞项 | 本机实测（`Device::as_hal::<Dx12>()` → `ID3D12Device::GetAdapterLuid()` vs DXGI `AdapterLuid`） |
| wgpu 30 该适配器上 `TEXTURE_FORMAT_NV12 = true`，且 R8/Rg8/R16/Rg16 均支持 `BIND | COPY_DST`（T1 上传路径成立） | 本机实测（`Adapter::get_texture_format_features`） |
| 硬解能力**不能以 OS 广告的 profile 列表为准**（HEVC 4:4:4 在 D3D11 profile 列表里存在，FFmpeg 实际仍软解） | 本机实测 |

仓库当前**没有任何 Rust 代码**，PC 端为「未开始」。

## 3. 方案与取舍

### 3.1 默认选择（可否决）

| 项 | 默认 | 理由 |
|---|---|---|
| 首个平台 | **仅 Windows** | 本机即 Windows，能立刻实测；三平台并行会把 spike 变成工程 |
| 帧通路 | **只做 T1**（`av_hwframe_transfer_data` 回读 → 上传 NV12 两平面 → 着色器转 RGB） | T0 零拷贝在 Linux 上已知受阻（NV12 dma-buf 导不进 wgpu），且 `unsafe`；先把 T1 跑通拿到基线 |
| 测试源 | **本地样片文件**，不用手机 | 与 agent 完全解耦，spike 不阻塞在设备侧 |
| 样片生成 | **用本机 `ffmpeg.exe` 生成**（含 1440x3200 纵向超长 + 1080p/720p 对照） | 无需等待任何外部输入 |
| 工程位置 | **`pc/`（新 Cargo workspace）+ `pc/spike` crate** | 与 Gradle 侧（`agent/`、`app/`）平级，互不干扰 |
| UI 复杂度 | 单窗口 + 视频面 + 一行状态（解码器名 / 分辨率 / 路数 / FPS / CPU） | spike 只需可观测，不需要产品 UI |

### 3.2 被否的做法

| 做法 | 否掉原因 |
|---|---|
| 一开始就做零拷贝（T0） | 平台障碍已确认（Linux NV12 dma-buf），且 `unsafe` 互操作会同时引入两类未知；先把 T1 基线拿到 |
| 用 `ffmpeg-sidecar` 子进程 | 每帧多一次进程间拷贝，拿不到 GPU 帧，与硬解目标冲突（技术栈已否） |
| 三平台并行 | spike 结论会互相稀释；Windows 先行拿到结论再复制 |
| 直接在 `:agent` 或 `:app` 里试 | 那是 Android 模块，跑不了 wgpu 桌面栈 |
| 引入 `egui_taffy` 等布局库 | spike 不需要弹性布局 |

### 3.3 容量探测与准入控制（本 spike 要落地的最小实现）

平台硬解器的**并发上限无标准 API**，所以不采用「压力测试探测」，而采用 **准入控制**：
**每新增一路就是一次真实探测**，失败点就是容量数据点。

**A. 静态能力探测（启动时一次，可缓存）**

| 探测项 | 手段 | 可靠性 |
|---|---|---|
| 可用硬解设备 | `av_hwdevice_iterate_types` / `av_hwdevice_ctx_create` | 可靠 |
| 每种解码器支持的 codec / profile / pix_fmt | `avcodec_get_hw_config(codec, i)` | 可靠 |
| 单路尺寸范围与对齐 | `av_hwdevice_get_hwframe_constraints`（`AVHWFramesConstraints`） | **不可靠** —— D3D11VA / dxva2 上多返回规范范围而非设备能力 |
| 显存预算 | DXGI `IDXGIAdapter3::QueryVideoMemoryInfo`（per-process video memory budget） | 近似值，**仅 Windows**；不代表可用于解码会话的余量 |
| 解码会话计数 | NVIDIA NVML（厂商专属） | 仅 NVIDIA；可作后门，不作依赖 |

**查不到、只能试错的项**（这也是准入控制存在的理由）：

1. **并发解码会话上限** —— NVDEC / D3D11VA / VideoToolbox 均无标准 API；
2. **实际可用显存与碎片** —— wgpu 无 API；DXGI 只给 per-process 预算近似；
3. 每路解码的真实内存开销；
4. 系统内存 / PCIe 带宽瓶颈；
5. 驱动是否真的把某 profile 跑在硬件上（`supported` ≠ 真在硬件上）；
6. 解码器内部缓冲深度与端到端延迟；
7. **零拷贝互操作（T0）能否建立** —— 取决于驱动 × wgpu 后端 × 帧格式组合，只能实试；
8. 长跑稳定性（显存泄漏、驱动复位）；
9. 同 GPU 被其他进程占用后的剩余能力；
10. 双 GPU（iGPU 解码 + dGPU 渲染）的跨适配器互操作可行性 —— **半可查**：能比对 LUID 判断是否同一适配器，但性能后果不可预知。

**规则：探测给候选，试错给结论**；缓存的是实测结果，不是探测结果。

**B. 准入流程（新增一路时执行；`Ledger` 为预算账本）**

```
1. 预算预估：cost = estimate(codec, w, h, fps)      // 解码器显存 + 纹理字节数 + 上传带宽
   若 used + cost > budget * safety(0.9) → 直接拒绝（原因：预算不足），不试探
2. 端到端最小帧（关键：不只测解码器）：
   复用 hw device → 建 decoder → **解出首帧（带超时）**
   → ★**硬校验：帧必须是硬件帧**（`hw_frames_ctx != null` / `format == AV_PIX_FMT_D3D11`）
   → av_hwframe_transfer_data → 创建 NV12 / P010 平面纹理 → 上传 → 画一帧
3. 任一步失败 → **完整回滚该路全部资源**，返回**带失败阶段**的错误
   （建解码器失败 / 首帧超时 / **非硬件帧（即静默软解）** / 回读失败 / 纹理创建失败 —— 五类要分开）
4. 成功 → 计入账本，进入稳态，并纳入运行期看门狗
```

> ★ **"硬校验"为什么必须单独存在**：FFmpeg 对不支持的 profile / 尺寸**不报错，而是静默回落到软解**
> （实测见 [`tech-stack/pc.md` §2](../spec/tech-stack/pc.md)）。所以「建解码器成功」「没有报错」「退出码 0」**都不能证明**走了硬解，
> 唯一可靠判据是**帧本身是硬件帧**。CLI 等价验证：`-vf hwdownload,format=nv12|p010` 返回 0。

**这一步必须覆盖整条链路**：真正耗尽的往往是**显存（纹理）**而不是解码会话数，
若只测「解码器能否创建」，会在多路纹理分配时才发现问题 —— 那时已有路已经在跑。

**C. 运行期看门狗**（针对「能创建 ≠ 能长跑」）

监测：单路长时间无输出帧、`transfer` 失败、纹理分配失败、DXGI 预算跌破阈值。
触发后**回收该路**（踢掉并明确告知原因）—— **不降分辨率 / 帧率**。

> 注意区分两种情形：**新增被拒**（超容量，不踢已有路）与**已在跑的路崩了**（本地资源耗尽，必须回收）。

**D. 结果缓存（避免每次启动都试错）**

- key = **GPU 型号 + 驱动版本 + codec + 分辨率档**，value = 已验证的可持续路数。
- 下次以缓存值起手（快路径），但仍走一次准入校验（环境可能变）。
- **驱动版本必须进 key** —— 厂商会改并发上限（NVIDIA 就调整过）。

**E. 裕度与可测性**

- 上限取「实测最大 − 1」或按 90% 预算设阈值，不在悬崖边运行。
- 提供**故障注入开关**（强制第 N 路建解码器失败 / 首帧超时）：
  否则回收与回滚代码永远不会被执行，等于没写。

### 3.4 FFmpeg dev 包获取（本 spike 必须先解决）

按技术栈已定：**动态链接共享库 + 随包分发**。Windows 侧需要 `include/` + 导入库（`.lib`）。

| 候选 | 备注 |
|---|---|
| BtbN `ffmpeg-master-latest-win64-*-shared` | 提供 `include/` 与共享库；**导入库是否存在需实测确认** |
| vcpkg `ffmpeg`（动态） | 可控，但首次构建慢 |
| 自建 | 最费时，仅在前两者都不可行时考虑 |

选定后必须记录**来源、版本、校验值**，因为要随包分发（LGPL 合规相关）。

## 5. 实施步骤

1. **建 `pc/` workspace 与 `pc/spike` crate**，确认 `cargo run` 能起一个空 egui 窗口
   （`eframe` + wgpu 后端，`cargo build` 通过）。
2. **解决 FFmpeg dev 包**（§3.4），让 `ffmpeg-next` 能编译链接最小程序，打印
   `avcodec_configuration()` 与版本。
3. **写能力探测程序**：枚举硬解设备与解码器，输出每个候选的 codec/profile 与
   **输出像素格式**，以及可上传的软件像素格式列表。**不要试图取分辨率范围 —— 没有这个 API**；
   尺寸只在准入时按实际参数校验。→ 验收 5。
4. **生成样片**：用本机 `ffmpeg.exe` 生成 H.264 / HEVC、4:2:0、8-bit 的样片：
   720p / 1080p / 1440x3200，各 60 秒，带**时间戳水印**（用于延迟量化）。
5. **单路硬解播放**：`hwaccel` 解码 → **首帧硬校验（必须是硬件帧）** → `av_hwframe_transfer_data`
   → NV12 / P010 平面纹理 → wgpu 着色器转 RGB → `register_native_texture` 上屏。→ 验收 1、2、3。
6. **超长尺寸测试**：1440x3200 样片跑一遍，记录**首帧硬校验**的判定结果
   （能硬解 / 判定为无法硬解并给出我们自己的错误）。→ 验收 4。
7. **多路并发 + 准入控制**：按 §3.3 实现「预算账本 + 端到端最小帧准入 + 完整回滚 +
   运行期看门狗 + 结果缓存」，逐路增加直到失败；在 720p / 1080p / 1440x3200 各做一遍，
   记录失败点、**失败阶段**与原始错误。→ 验收 6、7。
8. **延迟量化**：从样片取出帧时间戳，记录「解码完成 → 提交上屏」的耗时分布（P50/P95）。→ 验收 8。
9. **写实测报告**：数据与结论追加为独立文档（`docs/` 下新建实测记录），并在 `code-map.md` 登记。

**不做**：协议与协商消息、输入注入、agent 侧任何改动、三平台适配、T0 零拷贝、打包分发。

## 6. 验证方式

- 每步都有**可复核的原始输出**（命令 + 完整日志），不接受「应该可以」。
- 硬解必须自证：输出实际解码器名、hw 设备类型、以及 `av_hwframe_transfer_data` 的目标格式
  （应为 NV12 等硬解输出格式，不是 `yuv420p` 之类的软解路径特征 —— 以实测为准并记录）。
- 容量数据必须是**多路同时解码**（不是单路重复计时），否则测不出并发上限。
- 结论若与技术栈里的假设冲突（尤其「不设固定上限」的可行性），**先回讨论再改文档**。

## 7. 风险与回滚

| 风险 | 应对 / 回滚 |
|---|---|
| Windows 上拿不到可链接的 FFmpeg dev 包 | 退到 vcpkg；再不行自建（记录耗时，作为技术栈未决项 3 的输入） |
| `ffmpeg-next` 对当前 FFmpeg 版本（9.x）支持滞后 | 改用 `ffmpeg-the-third` 类分支或降到受支持的 FFmpeg 主线版本；记录结论 |
| T1 回读的 CPU/带宽在目标分辨率下不可接受 | 数据说话：若不可接受，回到技术栈讨论 T0 或改用 Vulkan Video 路线 |
| 1440x3200 无法硬解 | 结论直接约束 agent 侧编码参数与虚拟屏尺寸选择（技术栈未决项 6） |
| egui/wgpu 与 ffmpeg 的版本冲突（wgpu 主版本迁移频繁） | 锁小版本；冲突无法调和时记录并回讨论 |
| spike 代码变成"半成品产品" | spike 是**一次性验证代码**，验收后按结论决定保留/重写；不承诺演进 |
