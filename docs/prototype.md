# 原型项目（背景参考）

> **本仓库唯一允许出现的原型入口。** 其他文档需要提及原型时只链接本文件，
> 不直接链接原型内部文件 —— 避免路径与结论散落到各处。
>
> 本仓库是**重构**，不是原型的补丁：同一个问题在新结构下会有不同解法，很多设计会改。
> 原型的一切结论（含测试验证）**对本仓库不适用**，必须重新验证。

## 2. ⚠️ 使用界限

| 可以用 | 不可以 |
|---|---|
| 读原型代码来**避坑**、理解平台行为 | 把原型文档当**规范来源** |
| 借鉴它踩过的坑的**方向**（现象层面） | 把它的**结论与数值**当本仓库的验收标准 |
| 作为"这条路有人走过"的存在性证据 | 假定它的测试验证在本仓库仍然成立 |

以下内容**一律作废、必须重新验证**：

- 原型的性能 / 码率 / 帧率 / 体积等实测数值；
- 原型的日志格式、命令行参数名、协议字段与端口；
- 原型的实机观测结论（某 flag 组合的具体数值、某设备 / 某编码器的行为等）；
- 原型的验收命令与期望输出、里程碑完成情况。

原因：重构会改结构、改协议、改日志与参数名，也会改部分设计取舍。
原型的观测值只属于原型那一版实现与其当时的环境。

---

## 3. 怎么用

1. 需要背景时**先读本文件**，再按 §1 的表按需打开原型路径；
2. 任何来自原型的结论，导入本仓库时必须：
   - 标注为**待验证**，不得写成硬约束；
   - 在 `docs/plans/` 方案文档里说明重构后如何验证（流程见 [`docs/spec/workflow.md`](spec/workflow.md)）；
   - 实机验证通过后，才允许写进 [`docs/spec/agent/module.md`](spec/agent/module.md) 之类的规范文件；
3. 判定困难的条目：**以本仓库的实测为准**，原型只提供方向。
