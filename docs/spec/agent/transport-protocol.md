## 1. 统一框架

```
[1B 类型][4B 负载长度 N][N 字节负载]
```

| 项 | 约定 |
|---|---|
| 长度 | **= 负载长度**（**不含头**） |
| 上限 | **N ≤ 16 MiB** —— 超限即**断连**（防对端声明巨大长度炸内存） |
| 读循环 | `readFully(5)` → 类型 + 长度 → **校验上限** → `readFully(N)` ⇒ **头定长、循环不分叉** |
| 负载结构 | **完全由类型决定** |

**写的方式**：**头单独 `write`，数据再 `write`** ⇒ 帧数据**零拷贝直写** ✓
（合并成一次 `write` 反而要拷贝整帧 ✗）

**不需要"通道 / 多路复用"机制** —— `sender` 是唯一写者，且**控制队列优先于帧队列**
（[`agent/runtime-threads.md`](runtime-threads.md) §6）⇒ 优先级在**发送调度**里解决 ✓

## 2. 帧的负载（类型 `0x01`）

```
[1B flags][8B pts_us][编码数据（Annex-B）]
```

| 字段 | 为什么 |
|---|---|
| `flags` | bit0 = **关键帧**。**显式给**，不让 PC 去扫 NAL（`workflow.md` §4「不依赖默认值」） |
| `pts_us` | `presentationTimeUs` —— PC 做**渲染节拍 / 抖动缓冲**要用 |
| 数据 | **Annex-B**（`00 00 01` 起始码），`MediaCodec` 的原生输出 |

**帧不带 `streamId`** —— 一条连接 = 一块屏 ✓
**帧不带 CRC** —— 见 §3.3。

## 3. 控制消息的负载

```
[类型][4B 长度][4B CRC32][UTF-8 JSON]
                      └─ CRC 覆盖 [类型][长度][JSON]
```

### 3.1 为什么加 CRC（**理由要说准**）

| 你以为的威胁 | 实际 |
|---|---|
| 传输中字节被改 | **传输层已经防了**：adb（USB bulk 有 CRC）+ TCP（16 位校验和）⇒ 概率极低 |
| **真正的问题** | ① **失步** —— 读循环一旦读错长度，后面全部乱套，且**无法自我恢复**；② **实现 bug**（字段顺序写错、结构体对不上） |

⇒ CRC 在这里是**「失步检测器 + 实现自检」**，不是防线路噪声。
**失步是静默的** —— 不检测就会一直解析垃圾，所以更值得加 ✓

| 项 | 决定 |
|---|---|
| 算法 | **`java.util.zip.CRC32`**（JDK 自带，**零依赖**；误检率 2⁻³²） |
| 位置 | 控制消息负载的**首 4 字节** ⇒ **框架头仍是定长 5 字节，读循环不分叉** ✓ |
| 覆盖 | **`[类型][长度][负载其余部分]`** —— **连头部一起保护**（头部损坏最危险） |
| 失败 | **断开该连接**（协议级错误 ⇒ 单路级）。**失步后无法重同步** —— 长度前缀 + CRC 不提供重同步锚点，只能重连 |

**代价**：控制消息每秒几条、每条几百字节 ⇒ CRC32 是**微秒级**，可忽略；心跳也带 ✓

### 3.2 负载 = UTF-8 JSON，用 **Gson** 序列化

| 项 | 决定 |
|---|---|
| 格式 | **UTF-8 JSON**（文本，logcat / 抓包可直接读） |
| 库 | **Gson**（**已实测**在 `app_process` 可用，**含反射 DTO**） |
| 依赖政策 | **零依赖政策的唯一例外** —— 登记在 [`agent/module.md`](module.md) §4 |
| 两条配套 | ① `rules.keep` 必须 **`-keep` 全部协议 DTO**（Gson 靠反射访问字段，R8 看不见会删）；② **必须保持单 dex**（`app_process` 只加载 `classes.dex`） |

**视频帧绝不用 JSON** ✓

**指令（`0x20`）用「信封 + 载荷」两段式解析**：先解**信封** `cmd` + `requestId`，再按 `cmd` 把
**`payload`** 解成对应载荷结构体 —— 载荷字段名**固定 `payload`**；**无字段指令省略它**
（`stopAgent` / `endSession` / `requestSyncFrame`）。载荷结构体**不再携带** `cmd` / `requestId` ✓
（字段与形状见 [`agent/transport-messages.md`](transport-messages.md) §2.3 与 [`agent/transport-shapes.md`](transport-shapes.md) §2 / §5。）

### 3.3 帧不带 CRC 的后果（记录，不是问题）

帧的**长度字段**若损坏 ⇒ 读循环也会失步。但：
- 传输层有校验 ⇒ 概率极低；
- 一旦失步，**下一条控制消息的 CRC 会失败** ⇒ 断连重连；**心跳每 10s 一条** ⇒ **最迟 10s 内发现** ✓

## 4. 类型分段

| 值 | 方向 | 消息 | 负载 |
|---|---|---|---|
| `0x01` | agent→PC | **视频帧** | **二进制**（§2） |
| `0x10` | PC→agent | 握手（协议版本） | JSON |
| `0x11` | agent→PC | 握手应答（协议版本 + 自身状态） | JSON |
| `0x12` | PC→agent | 请求能力表 | JSON |
| `0x13` | agent→PC | 能力表 | JSON |
| `0x20` | PC→agent | **指令** —— `{"cmd":"…","requestId":N,"payload":{…}}`（无字段指令省略 `payload`） | JSON |
| `0x21` | agent→PC | **指令回报** —— `{"requestId":N,"ok":…,…}` | JSON |
| `0x22` | agent→PC | **主动上报**（屏已释放 / 子系统不可用 / fatal） | JSON |
| `0x30` | 双向 | 心跳 | JSON |

**"指令"只占一个类型值**，具体是哪条指令放在 JSON 的 `cmd` 字段里 ⇒ 类型表只有 9 个值 ✓
（按功能分段留空档：`0x0x` 帧 / `0x1x` 握手与能力 / `0x2x` 指令与上报 / `0x3x` 心跳）

## 5. 不需要分片（收口 `launch.md` §1 的待定项）

TCP / AF_UNIX 都是**字节流** ⇒ 「**长度前缀 + 读到够**」天然解决**任意大小**的消息 ✓
只有"定长缓冲"式协议才需要分片 ⇒ **本协议不做分片**，只需 §1 的**长度上限**。

## 6. 其他约定

| 项 | 约定 |
|---|---|
| **字节序** | **小端**（两侧都是小端机器；"不依赖默认值" ⇒ 显式写明） |
| **`requestId`** | **PC 生成**、单调递增、4 字节整数；**放 JSON 里**（不放框架头 —— 心跳的负载可以是空的）；**回报必须携带同一 id**；**重发合法**（同一 id 可重复出现，`launch.md` §2 允许连发/重发）；**心跳与主动上报不带** |
| **参数变更** | **不需要独立指令** —— 重发「申请屏幕」带同一 `streamId` + 新参数（[`agent/transport-handshake.md`](transport-handshake.md) §6） |

  **控制消息负载** = `CRC32 + UTF-8 JSON`（CRC 覆盖 `[类型][长度][负载其余]`，理由是

  **类型表只 9 个值**（"指令"占一个，指令名在 JSON 的 `cmd` 里）；
  **不做分片**（收口 `launch.md` §1）；字节序**小端**；`requestId` **放 JSON 里**。
