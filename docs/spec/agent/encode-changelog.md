- **2026-10-06 初版**：从 [`agent/display.md`](display.md) 拆出的 F3 骨架（6 项待定）。
- **2026-10-06**：**编码器能力探测**定稿 —— 取法（公开 API `MediaCodecList`）、
  本机实测参考值、**并发路数的协商规则 `min(PC 上限, 系统声明值)`**，
  以及"声明值只是上界候选、必须逐路验证是硬编、最终以试跑为准"三条纪律。
  变更记录改为**记在本文件**（原约定记在 `display.md §7`，随拆分失效）。
- **2026-10-06 决定 + 实测**：**低延迟** —— **一律开启、不作可配参数**；
  实测 `PARAMETER_KEY_LOW_LATENCY` **被接受但无可观测效果**（本机编码器默认已在低延迟态），
  并记录**延迟基线**（1440×3200@60：中位 ~22 ms、p90 ~25 ms，且不随时间增长 ⇒ 能持续跟上 60fps）。
  另记录编码器默认值（`prepend-sps-pps-to-idr-frames` 默认 0、`profile` 默认 High、
  **`color-standard` 输入/输出不一致**等）。
- **2026-10-06 决定**：**码率** —— PC **二选一**表达（**bpp 系数**按 `宽 × 高 × 刷新率` 算，
  或**直接给码率**）；**agent 不自主改码率**（不做自适应降码率）。
  由此记下留给 F4 的推论：**拥塞信号必须由 F4 送回 PC**，agent 不会自救。
- **2026-10-06 决定**：**载体** —— 本子系统的编码参数都是 **「申请屏幕」指令**的字段，
  与屏参数同一条指令、由 PC 选择（见 [`agent/display.md`](display.md) §2.0）。
- **2026-10-06 实测（色彩元数据）**：用「已知纯色 → 编码 → ffprobe 读 SPS VUI → 解码成 YUV
  反推矩阵」测出：**`MediaFormat` 报的色彩字段不可信**（输入格式报 BT709，实际是 BT601）；
  **码流 VUI 与内部矩阵自洽**，8 色往返偏差 ≤2/255；
  `KEY_COLOR_STANDARD` 会**同时**改变内部矩阵与 VUI。据此定下：**色彩字段由 PC 选择、
  agent 一律显式设置（绝不依赖设备默认）**；PC 侧按码流声明转换；
  **不得相信 `getInputFormat()` 的色彩字段**。
- **2026-10-06 决定**：**格式组的选择规则** —— 统一为「**优先默认值 → 本机不支持则退到
  第一个支持的 → 绝不退软编**」：**codec 优先 `H.264`**、**位深优先 8-bit**、
  **profile 优先 `High`（H.264）/ `Main`（HEVC）**、色彩优先 BT709。
  同时把"**不依赖默认值**"立为**全局规则**（[`workflow.md`](../workflow.md) §4，
  并在 [`agent/module.md`](module.md) §8 禁忌里留指针）：**协议可缺省，代码必须显式设置 + 回读确认**。
- **2026-10-06 决定**：**能力表** —— 因为**缺省是按设备动态推导的**，PC 若不填就**无从预知**
  agent 会选什么。故 agent 必须上报**结构化能力表**：
  **枚举**（codec / profile / 位深 / 色彩，**有序**，供"退到第一个支持的"用）+
  **范围+步进**（尺寸 / 帧率 / 码率）+ **整数**（并发声明值），
  且**每一行都带「缺省取值」**、**逐编码器列出**。载体与时机归 F4。
- **2026-10-06 拆分**：实测数值表**整段提成 [`agent/encode-capability.md`](encode-capability.md)**
  （规范 vs 快照分离：规范长期有效，快照**换设备即作废**）。
  并新增硬要求「**不得假定任何"常见值"**」（对齐不一定是 16、不能按 mime/名字筛）。
- **2026-10-06 补测**：**能力查询必须用尺寸相关接口** ——
  帧率上限**随尺寸变化**（1440×3200 只到 217.6、1920×1080 到 480），
  扁平 `getSupportedFrameRates()` 不是真实约束；且 **`getAchievableFrameRatesFor` 与实测矛盾**
  （报 48.96 上限，实测稳定喂 60.014 fps）⇒ **判据用 `areSizeAndRateSupported` + 实跑**。
- **2026-10-06 决定 + 实测**：**尺寸与帧率的校验规则**（对齐 → `isSizeSupported`
  → `getSupportedWidthsFor/HeightsFor` → **`areSizeAndRateSupported(w,h,刷新率)`**；
  **PC 显式给的值不满足即拒绝、不静默修正**；缺省值也过同一套校验；刷新率要回读确认）。
  **并发 4 项验证跑完**，据实测新增"**尺寸相关的资源上限**"与
  "**start 成功 ≠ 能用（必须验证真出帧）**"两条；失败形态实测为**明确抛异常、无静默软编**，
  但跨设备的安全网纪律保留。
- **2026-10-06 决定**：**帧率 = 虚拟屏刷新率**（编码器 `KEY_FRAME_RATE` **同步刷新率**，
  只影响码率控制）；**关键帧间隔默认 1 秒**；改间隔要重建编码器，临时要 IDR 走按需参数。
- **2026-10-06 决定 + 实测**：**`PREPEND_HEADER_TO_SYNC_FRAMES = 1` 固定开启、不可更改** ——
  实测（3 秒 / 3 个 IDR）：设 `1` 时 SPS/PPS 各出现 **4** 次、**3/3 个 IDR 前紧跟 SPS+PPS**；
  设 `0` 时各只 **1** 次、**仅 1/3** 带参数集 ⇒ **每个 IDR 自带参数集**，
  **F4 不需要单独的 CSD 交换环节**，协议里也不需要这个字段。
- **2026-10-06 决定 + 实测**：**码率的表达与模式拆开** ——
  **协议层不互斥**（两个字段并存，**解析/装包最简单**；互斥只在 **PC 的 UI 层**保证）+
  **agent 保底优先级**（**系数 > 固定码率**；两个都给时按系数取并**回报**；都不给时用默认 bpp 系数推导）。
  前提实测：**`KEY_BIT_RATE` 必填**，不设直接抛异常 ⇒ 没有"交给编码器自动"这条路；
  **码率模式是独立参数**（缺省 **VBR**、实测**只支持 VBR 与 CBR**，CQ 不可用）。
- **2026-10-06 定稿**：**第 4 与第 6 项合并**为「**静止态可解码性**」——
  实测筛掉两条（静止时 `REQUEST_SYNC_FRAME` **无效**、`REPEAT_PREVIOUS_FRAME_AFTER` **未采纳**）、
  确认两条（**换面触发一次性渲染**、`resize` 改 DPI 可制造 damage）；
  定下路径：解冻走"换面 + **立刻请求同步帧**"、新客户端接入被其覆盖；
  **冻结方案定为 A**（保留编码器、不重建）。
- **2026-10-06 定稿**：**参数变更：一律重建（不热改）** ——
  撤销原「码率热改」结论（`PARAMETER_KEY_VIDEO_BITRATE` 不再使用）；
  定下唯一的重建流程（`setSurface(null)` → release 旧 → 新建 → `setSurface(新面)` → **请求同步帧**），
  并指出它**与"解冻"是同一条路径**。
- **2026-10-06 修订**：**"缓存 IDR"改为彻底不需要** ——
  「**换面**（`setSurface(null)` → `setSurface(同一面)`）+ **`REQUEST_SYNC_FRAME`**」
  能覆盖**全部四类**"需要 IDR"的时点（首连 / 重连解冻 / 参数变更 / 丢包与解码器重启），
  且**无 App 副作用**。由此"改 DPI 制造 damage"也彻底不需要。
- **2026-10-06 定稿**：**色彩字段缺省**按通用规则推导（**优先 `BT709 + FULL + SDR_VIDEO`**，
  依据 = 虚拟屏是 SDR + 内容是 sRGB + `FULL` 不浪费码值；PC 可覆盖、不支持则回退）；
  并补两条澄清（`LIMITED` 的代价、`SDR_VIDEO` **不代表**支持 HDR）
  与主屏显示特性实测（[`agent/encode-capability.md`](encode-capability.md) §1.3）。
- **2026-10-06 收尾**：**显式设置总表**（含 `max-bframes = 0`、`priority = 0`、
  `operating-rate` 不设、`latency` 不设）；关键帧间隔**暂不做 PC 可配**、
  多路**暂不设总量上限**、10-bit 与 **HDR 暂不做、留作后续特性**；
  **默认 bpp 系数定为 `0.1`**（策略常数，PC 可覆盖；1440×3200@60 ⇒ ≈27.6 Mbps）。
- **2026-10-06 F3 收口**：**两项实机数值决定不测**（0 占用基线与尺寸拐点**都不影响设计** ——
  前者是保守侧、后者由试跑决定）。**F3 六项全部已定，无待确认项。**

- **2026-10-07 允许软编回退（用户取向，模拟器验证）**：纪律 2 由「**绝不退软编**」改为
  「**优先硬编；没有硬编时退软编，并在上报里如实标记 `hardware=false`**」——
  能力表逐编码器带 `hardware`，`applied` 也带；PC 侧（`negotiate.rs`）优先硬编、
  只有软编可用才用它并**显式提示**。动因：无硬编环境（Android 15 模拟器）要能端到端出画。
  同一轮实测还定了两条实现细节：
  - **提示键走运行期 `setParameters`**（`prepend-sps-pps-to-idr-frames` / `max-bframes` / `priority`）——
    模拟器软编**拒绝**该键出现在 `format` 里（`configure` 抛 `IllegalArgumentException`，消息为空）；
  - **CSD 补到首个关键帧**：软编即使用运行期参数也不给 IDR 带 SPS/PPS（PC 侧报
    `AVERROR_INVALIDDATA`）⇒ agent 把编码器单独给的参数集与首个关键帧合并（**零拷贝纪律的唯一例外**）。
  实测：模拟器（`c2.android.avc.encoder`，软编）1280×720 / 1920×1080 / 1080×1080 / 1600×900 / 1024×768
  全部端到端出画；真机（`c2.qti.avc.encoder`，硬编）1920×1800 仍满屏、144 帧 0 丢弃 ⇒ **无回归**。
