## 1. 结论：握手只做**两件事**

**握手 = 版本校验 + 能力表协商。**
一切**状态操作**（认领冻结的屏、建屏、改参数）**全走指令**。

⇒ **「重连」与「首连」完全同构** —— 正是 [`agent/display-lifecycle.md`](display-lifecycle.md) §2 已写的
「**重连走正常连接流程，与首连完全一致**」。

## 2. 时序

```
PC                                          agent
 │  connect                                  │
 │ ── 首包：协议版本 ──────────────────────►  │ 校验版本（不匹配 ⇒ 回报双方版本 + 断开）
 │ ◄── 握手应答：协议版本 + 自身状态 ───────  │ 状态 = 就绪 /「无硬编编码器」
 │ ── 请求能力表 ────────────────────────►   │
 │ ◄── 能力表（编码器 / 格式组 / 范围步进 / 缺省）│
 │                                            │
 │  ← PC 求交集：自己的硬解 ∩ 能力表            │
 │    交集为空 ⇒ PC 侧明确失败                  │
 │                                            │
 │ ── 申请屏幕（streamId? + 全部参数）─────►   │ 校验参数可行性
 │                                            │  id 存在且冻结 ⇒ 比较参数：
 │                                            │     一致 ⇒ 解冻；不一致 ⇒ 重建
 │                                            │  id 不存在 / 为空 ⇒ 建新屏 + 分配 id
 │ ◄── 回报：streamId + 每个参数的实际生效值 ── │
 │ ◄── 帧（首个是 IDR，自带 SPS/PPS）───────── │
```

**PC 先说话**（agent 在监听、PC 主动连）。

## 3. 版本号：**精确匹配**

| 项 | 决定 |
|---|---|
| 形态 | **一个协议版本整数**（协议变更即 +1），与产品版本**分开** |
| 匹配规则 | **必须精确相等** |
| 不匹配 | **明确失败**：回报**双方版本号** + 提示"请重推 agent"，然后断开 |

**为什么精确匹配**：agent 是**推到设备上的 jar**，很容易残留旧版 —— 精确匹配能**立刻**发现
"设备上跑的是旧 jar"，而不是产生一堆诡异行为。

## 4. 能力表

### 4.1 **启动时构建一次**（设备级静态量）

| 项 | 决定 |
|---|---|
| 构建时机 | **agent 启动时一次**（见 [`agent/runtime-startup.md`](runtime-startup.md) §1 第 4 步） |
| 生命周期 | **全进程生命周期内不变**，所有连接共享同一份 |
| **无 `forceRefresh`** | 表是**静态**的（编码器不会变）⇒ 任何时候请求都返回**同一份**，重查没有意义 |
| 依赖 | 需伪装 Context（[`agent/display.md`](display.md) §2.2）⇒ 必须在**进程引导之后**构建 |

### 4.2 内容

编码器清单、格式组枚举、**范围与步进**、**缺省** —— 全部是设备级静态量
（结构见 [`agent/encode-probe.md`](encode-probe.md) §4）。

### 4.3 **不含动态额度**

**当前还能开几路** **不进能力表** —— 实测「实际能开几路由**试跑**决定」
（声明 16 / 1440×3200 实测只有 7，见 [`agent/encode-capability.md`](encode-capability.md) §4.1）
⇒ **agent 无法预告**。

⇒ **PC 只能直接试**：发「申请屏幕」⇒ 成功 / 失败。
**这不是准入控制** —— PC 侧不做任何容量处理（[`tech-stack/pc.md`](../tech-stack/pc.md) §3），
失败只可能来自**硬解不可用**等实质原因，不来自容量。
与 [`agent/encode-params.md`](encode-params.md) §5（不拒绝、不偷改已有路）一致。

## 5. 能力协商：**谁做什么**

| 角色 | 职责 |
|---|---|
| **agent** | 提供**能力表** + **可行性否决**（PC 选的参数我能不能编） |
| **PC** | **求交集**（自己的硬解能力 ∩ agent 能力表）+ **选择参数** + 下发 |

**为什么交集必须由 PC 算**：[`tech-stack/overview.md`](../tech-stack/overview.md) §5 未决项 7 锁的约束是
「**协商结果必须保证接收端能硬解**」，而**只有 PC 知道自己的解码器支持什么** —— agent 无从校验。
让 agent 求交集就得让它维护一份"PC 硬解能力模型"，纯属多余。

⇒ 落在历史上倾向的「**PC 决策 + agent 可行性否决**」上 ✓

## 6. `streamId` 在「申请屏幕」指令里，**不在握手首包**

| 情况 | agent 的动作 |
|---|---|
| 带 `streamId`，该 id **存在且冻结** | 比较参数：**一致 ⇒ 解冻**；**不一致 ⇒ 重建**（[`agent/encode-lifecycle.md`](encode-lifecycle.md) §2.2） |
| 带 `streamId`，该 id **不存在** | **显式回报**"该 id 不存在，已分配新 id"（PC 记错了 ⇒ 必须让它知道） |
| **不带** `streamId` | 建新屏 + **分配新 id** 并回报 |
| 该 id 已被**另一条活跃连接**持有 | **新连接取代旧连接**（[`agent/transport-topology.md`](transport-topology.md) §5） |

⇒ **`streamId` 只出现在「申请屏幕」指令与它的回报里** ⇒ **重连 = 首连 + 带个 id** ✓
⇒ 参数**永远**走「申请屏幕」⇒ 只有一条参数路径，不需要"重连专用"的参数下发 ✓

## 7. 解码配置：**不需要独立机制** ⭐

不变量 4 要求"接收端拿到配置前不能只发普通帧"。但 F3 已定
**`PREPEND_HEADER_TO_SYNC_FRAMES = 1`** ⇒ **每个 IDR 自带 SPS/PPS**。

⇒ 只要**第一个发出去的是 IDR**，PC 就自带了全部配置信息 ⇒ **不需要单独的配置消息** ✓
而"第一个是 IDR"由已定的「**换面 + 立刻 `REQUEST_SYNC_FRAME`**」保证
（建屏时换面天然触发渲染；解冻时换面同理，见 [`agent/encode-lifecycle.md`](encode-lifecycle.md) §1.3）。

**必须写进协议的一条**：码流是 **Annex-B**（`00 00 01` 起始码）——
这是 Android `MediaCodec` 的输出格式，**已实测**（[`agent/encode-pitfalls.md`](encode-pitfalls.md) 的 NAL 扫描即按起始码）。

## 8. 握手超时

**握手期沿用判活超时 `T_dead`（10s），不另设值** —— 两者都是"连上了但收不到消息"，
语义与处置一致（都是**断开 + 计入接入尝试失败**）✓
覆盖范围：从连接到握手完成（含能力表请求）。

| 项 | 决定 |
|---|---|
| 值 | **`T_dead` = 10s**（[`agent/runtime-observability.md`](runtime-observability.md) §2） |
| 超时后果 | **断开该连接** + **计入「接入尝试失败」（+1）** —— 对上 [`agent/transport-topology.md`](transport-topology.md) §4.1 的计数规则 |
