# `:agent` · 失败与退出（F6）

> 本文件是 [`AGENTS.md`](../../../AGENTS.md) 索引下的规范之一，属 [`agent/runtime.md`](runtime.md)（F6）的**错误策略与退出**部分。

> **启动阶段的失败**见 [`agent/runtime-startup.md`](runtime-startup.md) §5。
> **变更记录记在本文件 §6。**

**状态**：**已定**（2026-10-07）。

---

## 1. 四级 —— 按「**谁负责善后**」分

| 级 | 判据 | `agent` 的动作 | 状态改变 |
|---|---|---|---|
| **致命 fatal** | 进程**无法继续正确运行** | **全局收尾** → `System.exit(非 0)` | 终止 |
| **子系统** | **能力 / 机制缺失 ⇒ 重试无意义** | **标记该子系统不可用**，拒绝后续相关指令（回报同一原因） | 持久（会话内） |
| **单路** | 该路（该屏 / 该连接）不可用，**其余健康** | **回收该路资源** + 上报 | 局部 |
| **可恢复** | 本次操作失败，**重试可能成功** | **只上报失败原因**（带 `requestId`），**不动任何状态** | 无 |

⚠️ **"可恢复"的重试由 PC 负责** —— agent **不做跨指令重试**，只做**同一操作内的有限重试**。
依据：[`agent/launch.md`](launch.md) §2「请求-回报 / 无状态」（agent 不维护业务状态，由 PC 记忆）。

## 2. 归属判据

### 2.1 致命 —— 来源**只有三类**

| # | 来源 |
|---|---|
| 1 | **任何组件线程意外退出**（含未捕获异常）—— R2：**不做"部分存活"模式**（[`agent/runtime-lifecycle.md`](runtime-lifecycle.md) §6） |
| 2 | **启动阶段失败** —— 进程引导 / 参数非法 / 监听地址被占用（[`agent/runtime-startup.md`](runtime-startup.md) §5） |
| 3 | **`main` 自身异常**（`Looper.loop()` 抛出） |

⇒ **其余一切失败都不致命** —— 运行期**不会因为某条指令失败而退出进程**。

### 2.2 子系统级 —— 判据是「**能力缺失**」，不是「某次操作失败」

| 子系统 | 触发 | 后果 |
|---|---|---|
| 编码（F3） | **无硬编编码器可用**（[`agent/encode.md`](encode.md) 纪律 2：**绝不退软编**） | 拒绝后续「申请屏幕」，回报"编码不可用" |
| 拉起（F2） | `cmd activity` 不可用 / 被系统策略禁止 | 拒绝后续「打开目标应用」 |
| 输入（F5） | 注入被系统策略禁止 | 拒绝后续输入事件 |
| 传输（F4） | **监听地址无法绑定**（除"被占用"外，如权限） | **致命** —— 无传输则无事可做 |

⚠️ **并发额度耗尽不算子系统级** —— 它是**资源类**（可释放），PC 稍后可重试 ⇒ 归**可恢复**。

### 2.3 单路级

| 触发 | 动作 |
|---|---|
| 某条连接协议错误 / 握手失败 | 断开该连接（**不影响其他**） |
| **运行中 `CodecException`** | **拆屏**（释放该路资源）+ 上报；由 PC 决定是否重建 |
| 拉起 App 失败（未安装 / 被拒 / 超时 / 落到别的屏） | 按 [`agent/launch.md`](launch.md) §5 分类回报；**不回收屏** |

### 2.4 可恢复

| 触发 | 动作 |
|---|---|
| 建屏失败（**资源类**：并发额度耗尽、编码器忙） | 回报原因（含异常）；**不自动重试**、**不禁用子系统** |
| 接入失败（[`agent/display-lifecycle.md`](display-lifecycle.md) §2） | `main` 计数；**连续 `N` 次**才升级为「拆屏」（单路级动作） |
| socket 瞬时 `IOException` | **同一操作内重试 1 次**；再失败 ⇒ 按「连接断开」处理 |

### 2.5 升级规则：**不做自动升级**

- 唯一的例外是 [`agent/display-lifecycle.md`](display-lifecycle.md) §2 已定的「连续 `N` 次接入失败 ⇒ 拆屏」；
- 可恢复失败**反复出现**由 **PC** 决策（agent 无状态）；
- **单路失败不升级**（除非是线程死亡 ⇒ 致命）。

## 3. 对外表现（**与 F7 耦合**）

| 级 | PC 怎么知道 |
|---|---|
| 致命 | **尽力**发一条 fatal 消息（含原因）→ 收尾；socket 已坏时**只能靠退出码** |
| 子系统 | **首次**上报"X 不可用"；之后每条相关指令各回报**同一原因** |
| 单路 | 随该指令的 `requestId` 回报；**拆屏另发主动上报**（[`agent/runtime-lifecycle.md`](runtime-lifecycle.md) §7） |
| 可恢复 | 随该指令的 `requestId` 回报 |

⚠️ 这些"上报"走的是**协议消息**（归 **F4**）；**日志**是**另一条通道**（logcat，F7）——
两者不要混：**PC 需要的走协议，给人看的走 logcat**。

## 4. 退出码

| 码 | 含义 |
|---|---|
| `0` | **正常结束** —— 上游显式停止 / 全部组件正常结束 |
| `1` | **运行中致命错误** |
| `2` | **启动失败** —— 进程引导 / 参数非法 / 监听地址被占用 / **设备级前置失败**（CDM 关联拿不到、虚拟设备建不出来、隐藏成员缺失；见 [`agent/runtime-startup.md`](runtime-startup.md) §1.2） |

## 5. 终止信号

**实测（本机实体机 / Android 16 / `app_process`）：`SIGTERM` 与 `SIGINT` 都\*\*不触发\*\* shutdown hook** ——
进程被信号直接终止，退出码 `143` / `130`（= `128 + 信号号`）。Android 的 libcore 没有把这两个信号
接到 JVM 的 hook 链上，`addShutdownHook` **只在 `System.exit` / JVM 正常终止时**跑。

⇒ **可靠停止手段 = 协议指令 `stopAgent`**（**已实测**：回报 `ok` → 收尾 → 退出码 `0`）。
⇒ **`kill -9` / `pkill` 也安全** —— 强杀时系统照样回收虚拟屏
（[`agent/display-lifecycle.md`](display-lifecycle.md) §5），只是**不走收尾**。

**`addShutdownHook` 仍然保留**（不删）：

- 它在 `System.exit` 路径上确实会跑，是「收尾完成」与「进程结束」之间的同步点；
- 收尾没做完时由它兜住：hook 里 **设全局停止标志 → 等 `teardownLatch`（超时 3s）→ 返回**；
- ⚠️ **`main` 的 `finally` 必须「先 `teardownLatch.countDown()`，再 `System.exit(status)`」** ——
  否则 **hook 等 main、main 等 hook ⇒ 死锁**（`System.exit` 会阻塞等所有 hook 结束）。

## 6. 收尾超时值

| 项 | 值 | 超时后 |
|---|---|---|
| 每个组件 `join` | 3s | 继续往下，**不阻塞收尾** |
| `sender` 排空队列 | 1s | 放弃剩余，`shutdownOutput()` |
| 收尾总上限 | 10s | 直接 `System.exit` |

（[`agent/runtime-threads.md`](runtime-threads.md) §9 的其余待定值不受影响。）

## 7. 变更记录

- **2026-10-07 终止信号修正（S1 实测）**：§5 的「**接管 `SIGTERM`**（`SIGINT` 同 —— JVM 默认都走
  shutdown hooks）」**不成立** —— 实测 `app_process` 下两个信号都不触发 hook，进程被直接终止
  （退出码 `143` / `130`）⇒ **可靠停止手段是协议指令 `stopAgent`**，`kill -9` 安全但不走收尾。
  `addShutdownHook` 保留（它是 `System.exit` 路径上的同步点与兜底）。
- **2026-10-07 定稿**：错误策略落盘。**四级按「谁负责善后」划分**（致命 / 子系统 / 单路 / 可恢复）；
  **致命来源只有三类**（线程意外退出 / 启动阶段失败 / `main` 异常），**运行期不会因指令失败退出**；
  **子系统级判据 = 能力缺失**（并发额度耗尽归可恢复）；**可恢复的重试由 PC 负责**；
  **不做自动升级**；退出码 `0` / `1` / `2`；**接管 `SIGTERM`**（含死锁规避）；
  收尾超时值（`join` 3s / 排空 1s / 总上限 10s）。
- **2026-10-07 VDM 实施**：退出码 `2`（启动失败）的**内涵扩大** —— 新增**设备级前置失败**
  （CDM 关联拿不到 / 虚拟设备建不出来 / 虚拟设备域隐藏成员缺失），依据
  [`agent/runtime-startup.md`](runtime-startup.md) §1.2。判据不变：**启动阶段失败 ⇒ fatal ⇒ 退出码 2**，
  因为此刻唯一的诊断入口就是退出码。
