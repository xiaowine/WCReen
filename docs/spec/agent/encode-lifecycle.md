## 1. 静止态可解码性（F3 第 4 + 6 项，**已定**）

**问题**：虚拟屏由 damage 驱动合成 ⇒ **静止时没有新帧**（[`agent/module.md`](module.md) §3 不变量 7）；
而客户端**第一帧必须是 I 帧**（不变量 8）。两者叠加就是本议题
（原第 4 项"静止画面无帧"与第 6 项"重建/解冻补关键帧"**是同一个问题**，已合并）。

### 1.1 先摆正：静止无帧本身不是问题

对远程桌面来说，静止时零帧正是**最优压缩**。要处理的只有两件事：

| # | 问题 | 对策 |
|---|---|---|
| **P1** | PC 把"长时间无帧"误判为断流 | **保活（心跳）与帧解耦**（F7）—— 判活看心跳，**不看帧** |
| **P2** | 需要 I 帧时拿不到 | 见 §1.3 |

### 1.2 实测：筛掉了什么、确认了什么

| 候选 | 结果 |
|---|---|
| 静止时 `PARAMETER_KEY_REQUEST_SYNC_FRAME` | ❌ **无效** —— 编码器**必须有输入帧**才能产 IDR（1.5 秒内 0 帧输出；对照：喂 1 帧 + 请求 ⇒ 出 1 帧且为 IDR） |
| `KEY_REPEAT_PREVIOUS_FRAME_AFTER` | ❌ **未被采纳**（设 100ms、静置 700ms ⇒ 0 帧） |
| **换输出面**（`setSurface(面)`） | ✅ **会触发一次渲染** —— 静止屏换面后新面收到帧，且是**一次性**的，之后重新静止 |
| **`resize(同尺寸, 改 DPI)`** | ✅ 能制造持续 damage（2.5 秒 11 帧）—— 但**有可见副作用** |

### 1.3 定稿：三条路径

| 场景 | 机制 |
|---|---|
| **冻结 / 解冻**（重连） | ① 冻结 `setSurface(null)` → ② 解冻 `setSurface(同一输入面)` → ③ **立刻 `REQUEST_SYNC_FRAME`** |
| **新客户端接入**（屏未冻结） | 按"一条连接 = 一块屏"，这只发生在重连 ⇒ **被上一条覆盖** |
| **丢包重同步 / PC 解码器重启** | **不需要缓存 IDR** —— 见 §1.7 |

### 1.4 冻结方案：**定为 A**（已定）

**A = `setSurface(null)` + 保留编码器**（不释放）。**不采用 B**（A + 释放编码器）。

理由（全部实测）：

- **复用同一个编码器解冻完全可行**，且**可反复**冻结 / 解冻；
- 解冻会**天然来一帧**（换面触发渲染）⇒ 不需要任何额外机制；
- B 的收益是"省一次重建开销"的反面 —— 但**重建本身没有收益**，反而多一次重建；
- B 唯一的独有价值是**释放一路并发额度**（本机 1440×3200 只有 7 路）——
  那属于**拆屏**（已有的"断开后立即释放"配置）的范畴，**不属于"冻结"**。

详见 [`agent/display-lifecycle.md`](display-lifecycle.md) §3.1 的实测表。

### 1.5 最后手段：**已不需要**

原先考虑用 `resize(同尺寸, 改 DPI)` 强制出帧。**现已不需要** ——
**换面**（`setSurface(null)` → `setSurface(同一面)`）是更干净的等价手段：
同样触发渲染，但**无 App 副作用**（输出面变化 App 感知不到），而改 DPI 会让 App 重新布局、画面抖一下。

⇒ 记录在案以免重复评估，**不作为手段使用**。

### 1.6 ⚠️ 两个必须记住的坑

1. **解冻后不请求同步帧 ⇒ 第一帧不是 IDR**（实测 IDR=0）⇒ 客户端**照样黑屏**；
2. **`KEY_I_FRAME_INTERVAL` 按"编码的帧"计、不是墙钟** ⇒ 静止屏上**周期性 IDR 永远不会来**
   ⇒ 需要 IDR 时**只能显式请求**（且要在**有输入帧**的时刻请求）。

### 1.7 关于"传输侧缓存 IDR"：**不需要**（已定）

**每一个"需要 IDR"的时刻都能用同一条手段解决**：

```
setSurface(null) → setSurface(同一输入面) → REQUEST_SYNC_FRAME
```

| 时点 | 怎么拿到新鲜 IDR |
|---|---|
| **首连**（建屏） | 建屏时 `setSurface(编码器输入面)` 本身就是"从无面到有面" ⇒ 换面触发渲染 |
| **重连 / 解冻** | 本来就是 `setSurface(null)` → `setSurface(同一面)` |
| **参数变更** | 重建编码器 + `setSurface(新面)`（§2.1） |
| **丢包重同步 / PC 解码器重启 / 主动刷新** | **主动做一次换面**（`setSurface(null)` → `setSurface(同一面)`）→ `REQUEST_SYNC_FRAME`<br>—— **已实测可行**，就是 §1.4 那条路 |

⇒ **四类时点全部覆盖** ⇒ **不需要缓存 IDR**。

**主动换面的代价**：屏会**重新渲染一帧**、并短暂无输出面 ——
对 PC 侧**无可见影响**（本来静止时也没帧），对 App **无副作用**
（输出面变化属 SurfaceFlinger 层面，App 感知不到）。

⇒ **决定：不做缓存**。`PREPEND_HEADER_TO_SYNC_FRAMES = 1` **仍保留**（它让每个 IDR 自带参数集，
是这条手段能"一帧自洽"的前提）。

> ⇒ 由此 **§1.5 的"改 DPI 制造 damage"也彻底不需要了**（换面更干净、无 App 副作用）。
> 若以后要支持"PC 主动要求刷新"，F4 需要一个对应的控制消息。

## 2. 参数变更：**一律重建**（F3 第 5 项，**已定**）

**决定：不存在"热改"。任何参数发生变化 ⇒ 重建编码器。**
（原「码率热改」的结论**已撤销**；`PARAMETER_KEY_VIDEO_BITRATE` 不再使用。）

### 2.1 重建流程（**只有这一条路径**）

```
① setSurface(null)        ← 解绑，屏停止输出；此后旧编码器可安全释放
② release() 旧编码器       ← 顺便释放并发额度（本机 1440×3200 只有 7 路）
③ 新建编码器              ← configure → createInputSurface → start
④ setSurface(新 inputSurface)  ← ⚠️ 换面会触发一次渲染 ⇒ 天然来帧
⑤ REQUEST_SYNC_FRAME      ← ⚠️ 必须！否则首帧不是 IDR（不变量 8）
```

**注意顺序**：① 必须在 ② 之前 —— 否则屏还在往一个即将失效的面上写。

> **这条路与"解冻"是同一条** —— 所以**参数变更 = 解冻**：
> 都是「换面 → 请求同步帧」。实现上可以共用一个函数。

### 2.2 什么情况不需要重建

参数**未发生变化**时不需要重建 —— 例如重连时 PC 下发的参数与当前编码器一致，
直接 `setSurface(同一输入面)` + `REQUEST_SYNC_FRAME` 即可（这就是冻结方案 A 的价值）。

### 2.3 各类参数的归属（**全部走重建**）

| 参数 | 变更方式 |
|---|---|
| 码率、码率模式、帧率（`KEY_FRAME_RATE`）、关键帧间隔、格式组（codec / profile / 位深 / 色彩）、尺寸 | **重建编码器** |
| **尺寸** 额外要 `resize()` 改屏（[`agent/display.md`](display.md) §2.1 的"成对改"） | 重建 + 改屏 |
| **DPI** | 只 `resize()` 改屏，**编码器不动**（像素数不变） |
| **刷新率、flags** | **建屏期参数、会话内固定** ⇒ 变更 = **回报"需重开会话"**（[`agent/display.md`](display.md) §2.1） |

**不需要运行期参数的场合**：临时要一个 IDR 用 `PARAMETER_KEY_REQUEST_SYNC_FRAME`
（按需，不算"参数变更"）。
