## 1. 为什么不搞全局状态机

**建屏与连接建立是解耦的**（[`agent/display-lifecycle.md`](display-lifecycle.md) §1 / §2），
且**断开不拆屏** ⇒ "有屏无连接"与"有连接无屏"都是**合法稳态**。
全局状态机会被迫展开成笛卡尔积，**反而丢掉两个子系统的既有语义**。

⇒ **两个自治状态机 + 一个只做"会话策略 + 终局"的协调者**（§5）。

## 2. 状态机 1：显示链路（屏 + 编码器，**焊成一个**）

**为什么合成一个**：零拷贝（[`agent/module.md`](module.md) §3 不变量 3）把屏的输出面与编码器的输入面焊死；
重建五步（[`agent/encode-lifecycle.md`](encode-lifecycle.md) §2.1）与收尾顺序
（[`agent/display-lifecycle.md`](display-lifecycle.md) §5）**全部成对**。
分开管只会制造"屏在而编码器没了"这种无意义中间态。

### 2.1 对外只有 3 个状态

编码器的 `未配置 / 已启动 / 已释放` 是**链路内部细节，不单独暴露** ——
参数变更一律重建，编码器从来不可被独立观察。

| 状态 | 含义 | 出帧 | 屏上 App |
|---|---|---|---|
| **无屏** | 无 `VirtualDisplay`、无编码器 | ❌ | 无 |
| **就绪** | 屏 + 编码器 + 输出面已绑 | ✅（有 damage 时） | 在跑 |
| **冻结** | 屏与编码器都在，`setSurface(null)` 解绑了输出面 | ❌ | **在跑，状态不丢** |

### 2.2 转移表（全部来自既有定稿文档，此处只是汇总）

| 从 | 到 | 触发 | 动作 |
|---|---|---|---|
| 无屏 | 就绪 | **申请屏幕**指令（参数随指令到达，[`agent/display.md`](display.md) §2.0） | `createInputSurface` → `createVirtualDisplay` → `start` → `setSurface(输入面)` → `REQUEST_SYNC_FRAME` |
| 就绪 | 冻结 | 连接断开 | `setSurface(null)` |
| 冻结 | 就绪 | 接入成功，**参数未变** | `setSurface(同一输入面)` → `REQUEST_SYNC_FRAME` |
| 就绪 / 冻结 | 就绪 | **参数变更** | `setSurface(null)` → `release` 旧 → 新建 → `setSurface(新面)` → `REQUEST_SYNC_FRAME` |
| 就绪 / 冻结 | 就绪 | 主动刷新（要 IDR） | `setSurface(null)` → `setSurface(同一面)` → `REQUEST_SYNC_FRAME` |
| 就绪 / 冻结 | 无屏 | **拆除触发集合** | `release` 屏 → `release` 编码器（**硬顺序**） |

**拆除触发集合**：上游显式结束 / 连续 `N` 次接入失败 / 致命错误 / 进程退出。
（**终止信号不在其列** —— 实测不触发 shutdown hook，见 [`agent/runtime-failure.md`](runtime-failure.md) §5。）

## 4. 合法组合表与不变量

> **本表是「每路」的** —— 一路 = 一块屏 = 一条连接（多路结构见 [`agent/transport-topology.md`](transport-topology.md)）。

| 链路 \ 连接 | 未连接 | 已连接 |
|---|---|---|
| **无屏** | 空闲（初始 / 拆屏后等待重连） | ✅ 合法 —— 刚接入还没申请屏幕（**枚举可用**，[`agent/launch.md`](launch.md) §2） |
| **就绪** | ❌ **不可达** | ✅ 正常串流 |
| **冻结** | ✅ **正常稳态** —— 等重连 | ⏸ 瞬态（接入成功 → 解冻之间） |

| # | 不变量 | 依据 |
|---|---|---|
| **L1** | **就绪 ⇒ 已连接** —— 有输出面就必然有人在看 | 建屏指令来自连接；断开必冻结 |
| **L2** | **断开 ⇒ 若屏存在则冻结**，否则保持无屏 | [`agent/display-lifecycle.md`](display-lifecycle.md) §2 |
| **L3** | **无屏 + 已连接 合法** —— 枚举 / 拉起不依赖屏 | [`agent/launch.md`](launch.md) §2 |
| **L4** | **冻结 ⇒ 屏与编码器都在** —— "App 状态不丢"的全部依据 | 冻结方案 A |

## 5. 协调者（`main`）

### 5.1 持有什么

**原则：协调者不镜像子系统状态。** 否则就是第二份真相，必然漂移。

| `main` 持有 | 为什么不能放子系统 |
|---|---|
| 组件完成计数 | 跨全部组件 |
| **接入失败计数（`N`）** | 事件来自 `reader`、动作在 `link` ⇒ **跨子系统策略**；**按路各一份**（[`agent/transport-topology.md`](transport-topology.md) §4） |
| PC 可配的会话策略项（`N`、断开后立即释放） | 跨子系统生效 |
| 全局停止标志 / 终局状态 | 唯一跨全部线程的东西 |

**`main` 不持有**：屏 / 编码器的任何状态、连接状态、当前参数
（建屏参数随指令到达；参数比较由 `link` 自己做）。

### 5.2 职责只有 3 类

| # | 职责 | 说明 |
|---|---|---|
| 1 | **持有跨子系统的策略** | **跨子系统的策略只允许存在于协调者** —— `reader` 只报事件、`link` 只执行命令，两者都不知道 `N` 是什么 |
| 2 | **聚合终止条件** | 组件完成计数 ⇒ `quitSafely()`；任一 fatal ⇒ 立即收尾 |
| 3 | **发起全局收尾** | **`main` 唯一编排的序列就是收尾序列**（[`agent/runtime-threads.md`](runtime-threads.md) §8） |

### 5.3 事件与命令接口

⚠️ **"编排"大部分不需要 `main`**：接入成功后的整串（应用参数 → 可能重建 → 解冻 → 补关键帧）
**全在链路状态机内**，是 `link` 内部的一条顺序代码。

| 事件 | 去向 |
|---|---|
| 断开 → 冻结 | `reader` → **`link`**（无需决策） |
| 接入成功（参数）→ 应用参数 + 解冻 + 补关键帧 | `reader` → **`link`**（整串在 `link` 内） |
| 接入成功 / 接入失败 / 断开 | `reader` → **`main`**（只用于计数与"断开后立即释放"策略） |
| 达 `N` 次 ⇒ 拆屏 | `main` → **`link`** |
| 停止 / fatal | `main` → **全部** |

同一件事既投 `link` 又报 `main` 是**刻意的**（`main` 要计数、`link` 要执行），**不是冗余**。

### 5.4 仲裁由队列串行化完成

**不需要额外的仲裁层** —— 每个 owner 的串行队列**就是**仲裁点：

- PC 连发两条参数变更 ⇒ 在 `link` 的指令队列里串行，天然互斥；
- 停止指令撞上正在执行的建屏 ⇒ `main` 先设停止标志，`link` 在执行间隙检查后退出；
- 两个客户端抢同一块屏 ⇒ 由 **`streamId` 认领规则**仲裁（[`agent/transport-topology.md`](transport-topology.md) §5）。

这就是"全模块不设业务锁"的收益兑现处。

## 6. 两条硬规则

| # | 规则 | 理由 |
|---|---|---|
| **R1** | **对子系统的命令必须幂等** | 协调者不镜像状态 ⇒ 它可能发出"拆屏"而屏已经没了。`link` 对"无屏时拆屏"必须是 no-op |
| **R2** | **区分「单次操作失败」与「线程死亡」** | 单次操作失败（组件不存在 / 被系统拒绝 / 拉起超时）在**本线程内分级回报**，不是 fatal；**线程意外退出一律 fatal** ⇒ 触发收尾。理由：**不做"部分存活"模式** —— `link` 死了帧通路断、`slow` 死了拉起指令永久排队，且"谁来报错"会变成一堆新待定项 |

**未捕获异常**由 [`agent/runtime.md`](runtime.md) §3.2 ① 的 `setDefaultUncaughtExceptionHandler`
兜住 ⇒ 报 fatal ⇒ 走收尾序列。

## 7. agent 主动上报的事件

PC 自己知道连接状态与它发过的指令 ⇒ **只有 agent 单方面改变的事实需要上报**：

| 事件 | 为什么必须报 |
|---|---|
| **屏已释放**（含原因：上游结束 / `N` 次失败 / 致命错误） | **PC 不知道**，且这是 `N` 次失败策略的后果 |
| **参数实际生效值** | [`agent/display.md`](display.md) §2.1 已定：每个生效值都回报 |
| 拉起失败 / 枚举结果 | [`agent/launch.md`](launch.md) §2 的请求-回报 |

**不需要"全局状态"消息** —— 判活看心跳（F7），其余各自回报。
