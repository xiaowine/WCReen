## 1. 单进程多路（已定）

**一个 agent 实例服务 N 路**；**一路 = 一块屏 = 一条连接**。

| 方案 | 判定 |
|---|---|
| **单进程多路** ✅ | 一个进程、**一个监听地址**（已实测支持多连接）、N 条连接 = N 块屏 |
| 每路一个进程 ❌ | **网络模式下 PC 没有 adb ⇒ 开不了第二路**（uid 2000 只能从 adb 起，[`agent/runtime.md`](runtime.md) §2.1.1）。即使让 agent 自己 fork 子进程，也只是**把多路实现进子进程** —— 复杂度更高，收益只有"隔离"，而隔离可以用**单路级错误处理**换到（[`agent/runtime-failure.md`](runtime-failure.md) §2.3） |

⇒ **多进程没有净收益**，成本（N 个 JVM、N 个监听名、进程管理）却实打实。

## 2. 「路」的定义与 `streamId`（已定）

三个对象，生命周期**互不同步**：

| 对象 | 创建 | 销毁 | 能活过连接断开吗 |
|---|---|---|---|
| **连接** | PC 连入 | 断开 / 判死 | ✗ |
| **屏 + 编码器** | 「申请屏幕」指令 | 拆屏触发集合 | ✅ **冻结后仍在** |
| **路映射（`streamId` → 屏）** | 首次建屏 | 拆屏 | ✅ |

**必须引入 `streamId`** —— 否则 PC 重连时 agent 认不出"这条新连接是来接那块冻结的屏的"，
**冻结就白做了**（等价于断开即拆屏）。TCP 新连接 ≠ 旧连接，两者没有任何天然关联。

```
建屏成功 ⇒ agent 分配 streamId 并回报
PC 记住   ⇒ streamId ↔ 它认为的那块屏
重连时    ⇒ PC 在握手首参里带上 streamId ⇒ agent 查表认领 ⇒ 绑定 + 解冻
```

**由 agent 分配**（自增序号）—— agent 自控 id 空间，PC 只负责记下来，
与「agent 不维护业务状态、PC 记忆」（[`agent/launch.md`](launch.md) §2）一致。

> 替代方案（按建屏参数匹配）**太脆**，不采用。

## 3. 进程内结构与线程归属（已定）

```
agent 进程（一个实例）
├─ main（协调者）· accept（监听+分派）· slow（枚举/拉起）   ← 进程级单例
├─ 路 #1 ─ reader（唯一读者）· link（屏+编码器）· sender（唯一写者）
├─ 路 #2 ─ …
└─ 路 #N ─ …
```

| 线程 | 归属 | 数量（N 路） |
|---|---|---|
| `main` | 进程级 | 1 |
| **`accept`** | 进程级 —— 监听 + `accept` + 分派 | 1 |
| `slow` | 进程级 —— 枚举 / 拉起（无状态） | 1 |
| **`reader`** | **每路** —— socket 读侧 | N |
| `link` | **每路** —— 屏 + 编码器 | N |
| `sender` | **每路** —— socket 写侧 | N |
| `input` | **每路** | F5 已定（[`agent/input.md`](input.md) §5） |

⇒ N = 7 时约 **25 条线程**，可接受。
**每路一套 `reader` / `link` / `sender` ⇒ 一路的网络抖动或编码异常不牵连其他路** ✓

## 4. 生命周期流转与计数语义（已定）

| 事件 | 动作 |
|---|---|
| PC 连入，**不带** `streamId` | 建一条"**未绑定**"的连接（可执行枚举；也可发建屏指令） |
| 「申请屏幕」带参数 | 建屏 → **分配 `streamId` 并回报** → 绑定到该连接 |
| 连接断开 / 判死 | **只冻结**（屏 + 编码器保留），`streamId → 屏` 保留；连接销毁 |
| PC 重连**带** `streamId` 且该路存在 | 查表 ⇒ **绑定 + 解冻 + 补关键帧** |
| PC 重连带 `streamId` 但**表里没有** | 视为新路（无屏），等 PC 发建屏指令 |
| 拆屏 | `release` 屏 → `release` 编码器，**删除映射**，释放一路并发额度 |
| 停止 agent | `accept` 停 → **每路**走 [`agent/runtime-threads.md`](runtime-threads.md) §8 序列 → `System.exit` |

### 4.1 `N` 次接入失败 —— 计数语义（收口 `display-lifecycle.md §2` 的待定项）

**计数规则**：

| 事件 | 计数 |
|---|---|
| **断开**（连接结束：正常断开 / 判死） | **+1** |
| **接入尝试失败**（连上了但握手 / 版本 / 参数 / 认证没过） | **+1** |
| **重连成功**（认领 + 解冻） | **清零** |
| 未带 `streamId` 的新连接（新路） | 不计（**没绑定该路**） |

**计数 ≥ `N`（缺省 5）⇒ 拆屏。**

> **USB 数据线松动**：断开（+1）→ 数秒后重连成功（**清零**）⇒ **不会累积** ✓
> 要触发拆屏，必须是**连续 `N` 次断开都没能重连成功**（或 `N` 次接入尝试失败）。

- **「断开后立即释放」= `N = 1` 的特例** —— 两个配置的关系由此明确；
- 缺省 `N = 5`。

## 5. 同 `streamId` 冲突：**新连接取代旧连接**（已定）

PC 重连带的 `streamId` 已被一条**活跃**连接占用时 ⇒ **关闭旧连接，新连接接管**。

理由：PC 是权威方（它声明了身份），且 **PC 崩溃重启后能立刻恢复**，不用等 30s 判死窗口。
这是"同一路的新连接取代旧连接"，与容量无关（**PC 侧不做任何容量处理**，不会因容量踢人）。

## 6. 传输层

| 项 | 状态 / 决定 |
|---|---|
| **监听地址** | **一个**（进程级，由 `accept` 线程持有）—— **已实测**：设备内 3/3、经 `adb forward` 3/3 |
| **连接方向** | **agent 监听、PC 主动连**（两种传输一致，`runtime-threads.md §5`） |
| **adb 通道** | 设备侧 `LocalServerSocket("<名>")`；PC 侧 `adb forward tcp:PORT localabstract:<名>` |
| **网络通道** | 设备侧 `ServerSocket(PORT)` |
| **重复实例检测** | **监听地址被占用**（**已实测**可靠地检测到活着的实例） |
| **多传输并存** | **待定** —— 倾向**一次只启用一种**（启动参数选），并存留后续 |
| **网络侧认证** | **待定** —— adb 通道天然有 adb 密钥认证；**裸 TCP 没有** ⇒ 认证**只在网络通道**需要 |
