## 1. 建立

由上游请求触发 —— agent **不自动建屏**。该请求是一条**显式指令**（「申请屏幕」，见
[`agent/display.md`](display.md) §2.0），**建屏与连接的建立是解耦的**。

## 2. 断开与重连（策略）

**核心模型**：断开时**不拆屏** —— **冻结 + 保持可接受新连接**；
**重连走正常连接流程**（与首连完全一致）⇒ 重连时**可以重新下发参数**。
推论：**参数只可能在连接建立时确定**，运行中不存在"原地改参数"
（**任何参数变更都走重建编码器**，见 [`agent/encode-lifecycle.md`](encode-lifecycle.md) §2）。

| 阶段 | 动作 |
|---|---|
| 断开 | **冻结**：`setSurface(null)`（方案 A/B 见 §3）；屏与 App 状态保住 |
| 等待 | 保持可接受**正常连接**（不区分首连 / 重连） |
| 接入成功 | 收到**带 `streamId`** 的「申请屏幕」⇒ 应用参数（[`agent/display.md`](display.md) §2.1）→ 解冻 → **补关键帧**（硬约束 8）→ 出帧 |
| 接入失败 | **连续 N 次失败 → 释放虚拟屏**；`N` 由 PC 配置，**缺省 5** |
| PC 可配 | `N`；以及**"断开后立即释放"**（不等重连）—— 由 **`setPolicy` 指令**承载（**可在任意时刻下发**），见 [`agent/transport-messages.md`](transport-messages.md) §2.3 |

> ⚠️ **"N 次"的计数语义（等待窗口时长、如何判定"一次失败"）取决于连接拓扑，而拓扑属 F4** ——
> 本文件只锁策略；**计数语义已定** —— 见 [`agent/transport-topology.md`](transport-topology.md) §4.1
> （断开或接入尝试失败各计一次，**重连成功即清零**）。

## 3. 冻结方案：**定为 A**（已定）

**前提事实**：零拷贝链路是 `虚拟屏输出面 = 编码器输入面`，所以"保留屏"**不等于**"只留一块空屏" ——
只要链路完整，屏上的 App 与编码都会继续跑。因此断开需要一个"**停输出但不丢状态**"的手段。

`VirtualDisplay.setSurface(Surface)` 是**公开 API**（不需要隐藏 API 技巧），能做两件事：

- 传 `null` → **解绑输出面**；
- 传另一个 Surface → **换输出面** —— ⚠️ **换面会触发一次渲染**（见 §3.1），这是解冻能"天然来帧"的原因；

| 方案 | 做法 | 省掉 | 保留 | 结论 |
|---|---|---|---|---|
| **A** ✅ | `setSurface(null)` | 停止出帧（编码器空转） | 屏 + **App 状态不丢** + **编码器可复用** | **采用**（实测见 §3.1） |
| B ❌ | A + `release()` 编码器 | 再省编码器的内存 / GPU / **一路并发额度** | 屏 + App 状态不丢 | **不采用** —— 重建没有收益，反而多一次重建；<br>"省并发额度"属**拆屏**（已有的"断开后立即释放"配置）的范畴 |

**解冻（重连）路径（已定）**：

```
解冻: setSurface(同一个 inputSurface)   ← 换面会触发一次渲染 ⇒ 天然来帧
      ↓ 紧接着
      REQUEST_SYNC_FRAME                 ← ⚠️ 必须！否则首帧不是 IDR（硬约束 8）
```

### 3.1 冻结 / 解冻实测（**方案 A**）

复用**同一个编码器**（不重建），冻结 `setSurface(null)`、解冻 `setSurface(同一个输入面)`。
**前置条件已验实** —— 先用连续两个窗口（2s + 2.2s）确认屏**确实静止**，再做冻结 / 解冻：

| 阶段 | 实测 |
|---|---|
| 屏确认静止 | 连续两窗口均 **0 帧** |
| **冻结** | 2 秒内 **0 帧** ⇒ 真的停输出 ✓ |
| **解冻**（不请求同步帧） | **10 帧、IDR 0** ⇒ **复用可行** ✓ |
| 解冻后**再观察 2 秒** | **0 帧** ⇒ **一次性爆发，之后重新静止** |
| 再冻结 / 再解冻（先请求同步帧） | 0 帧 / **10 帧、IDR 1** ⇒ 可反复 ✓ |

**三条结论**：

1. **换面会触发一次渲染** ⇒ 解冻**天然会来帧**（不需要额外机制），且是**一次性**的；
2. **编码器可复用、不重建** ⇒ 候选 A 成立；
3. ⚠️ **解冻后必须显式 `REQUEST_SYNC_FRAME`** —— 否则第一帧**不是 IDR**，
   而 `KEY_I_FRAME_INTERVAL` **按"编码的帧"计、不是墙钟** ⇒
   **静止屏上周期性 IDR 永远不会来**。

⇒ **候选 A 成立，且不需要重建编码器** ⇒ **方案定为 A**（**不采用 B** —— 重建没有收益；
B 唯一的独有价值"释放一路并发额度"属**拆屏**范畴，本机 1440×3200 实测只有 7 路）。

> **另一条被否的候选（记录以避免重复评估）**：`MediaCodec.setParameters(PARAMETER_KEY_SUSPEND, 1)`
> （编码器丢弃输入帧）—— 屏仍在合成渲染，**省得最少**，故不采用。

## 4. 实机验证结果

**§3 的三项已全部测过**（数据见 §3.1 与 [`agent/encode-pitfalls.md`](encode-pitfalls.md) §1 第 11–12 条）：

| # | 原未知 | 结论 |
|---|---|---|
| 1 | `setSurface(null)` 后是否**真的停止**为该屏合成 | ✅ **是** —— 冻结后**新增输出 0 帧** |
| 2 | 重新 `setSurface(输入面)` 后屏能否恢复出帧 | ✅ **能** —— 解冻后新增 10 帧；且**同一个编码器可复用**、可反复冻结/解冻 |
| 3 | 解冻后首帧是否为 I 帧 | ❌ **不是**（IDR=0）⇒ **必须显式 `REQUEST_SYNC_FRAME`**（请求后 IDR=1） |

**冻结时长：没有上限**（**已定**）—— 拆除由**事件**触发（`N` 次接入失败 / 上游显式结束 / 致命错误 /
进程退出），**不是超时** ✓ 见 [`agent/transport-topology.md`](transport-topology.md) §4.1 的计数规则。

⚠️ **代价**：冻结期间**保留编码器** ⇒ **占一路并发额度**（本机 1440×3200 只有 7 路）——
这是**有意的**；PC 有两条出口：`setPolicy{releaseOnDisconnect}`（走之前打开）或 `endSession`（立刻拆）。

## 5. 真正结束与异常

- **拆除触发**：上游显式结束 / **连续 N 次接入失败（见 §2）** / 致命错误 / 进程退出。
  （**终止信号不在其列** —— 实测 `SIGTERM` / `SIGINT` 不触发 shutdown hook，见
  [`agent/runtime-failure.md`](runtime-failure.md) §5；`kill -9` 由系统回收，见下。）
- **收尾顺序（硬约束）**：**先 `release()` 虚拟屏 → 再 `release()` 编码器**。
  顺序反了会让编码器的输入 Surface 在屏仍在渲染时失效。
- **进程异常退出（已实测）**：**系统会随 owner 进程死亡自动回收虚拟屏** ——
  `kill -9` 与 `halt(9)` 两条路径都验过（`dumpsys display` 屏数回落、屏名命中归零），
  屏上内容也**没有**跑到本机屏。实体机（Xiaomi / Android 16 / aarch64）与
  AVD（AOSP / Android 16 / arm64）**结论一致**。
  ⇒ **不需要**启动时扫屏名前缀清理残留（原预防措施作废）。
- **拆屏不得改变本机屏状态**（见 [`agent/display.md`](display.md) §5 验收判据 4）。
