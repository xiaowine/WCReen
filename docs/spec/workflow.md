# 工作流规范：先讨论 → 再写方案 → 用户批准后才实施

> 本文件是 [`AGENTS.md`](../../AGENTS.md) 索引下的规范之一。
> 适用于**任何涉及代码改动**的请求。

---

## 1. 未讨论不动代码

收到涉及**新增 / 修改 / 删除 / 重构 / 依赖变更 / 构建配置变更**的请求时，
默认进入 **讨论阶段**，**不得**直接 `edit` / `write` 代码文件。

讨论阶段必须完成：

1. **复述目标**，确认理解无歧义；
2. **调研现状**：读相关源码与文档，给出基于事实的现状描述（引具体文件与符号）；
3. **列出约束**：尤其是 [`agent/module.md §3`](agent/module.md) 的 8 条不可协商不变量；
4. **给出 ≥1 个方案**及其取舍；有多个可行方案时说明推荐哪一个及理由；
5. **显式标注**风险、未知项与需要用户拍板的分叉点。

### 可直接执行、无需讨论的例外

- 纯问答、调研、解释、代码阅读；
- 只读探查（搜索 / 看文件 / 跑非破坏性命令）；
- 用户明确表示「直接改 / 开始实现 / 不用讨论」；
- 纯文档修订且**不涉及行为约定**（在用户指定范围内）。

---

## 2. 方案文档：必须落盘并长期保留

讨论达成一致后，把实现方案写入：

```
docs/plans/YYYY-MM-DD-<kebab-slug>.md
```

例：`docs/plans/2026-10-06-virtual-display-reconnect.md`

### 2.1 必备小节

| 小节 | 内容 |
|---|---|
| 背景与目标 | 要解决什么问题；验收标准（可观测、可复现） |
| 现状调研 | 现有代码 / 契约的事实依据，带文件与符号 |
| 方案与取舍 | 候选方案、选择理由、被否方案及原因 |
| 影响面 | 涉及的文件 / 模块 / 对外契约（协议、CLI、部署路径） |
| 实施步骤 | 可执行的有序步骤 |
| 验证方式 | 如何证明改对了（命令 / 场景 / 期望输出） |
| 风险与回滚 | 已知风险、失败模式、回滚手段 |
| 未决问题 | 尚未定论、需要用户决策的点 |

### 2.2 约束

- 方案文档是**长期产物**：实施完成后**不得删除、不得覆盖**；后续变更以**新建文档**记录。
- 方案文档只描述「将要做什么」与「为什么」，不夹带无关改动计划。
- 文件名用日期前缀保证可排序；slug 用英文小写连字符。
- 目录占位见 `docs/plans/.gitkeep`。

## 3. 实施闸门

- 方案文档写完后**停止**，等待用户**明确批准**才开始实施；批准前不改任何代码。
- 用户可批准**全部 / 部分 / 要求调整**；实施范围**严格以当次批准的方案为界**，不得顺手扩大。
- 实施中发现方案需要偏离时，**回到讨论**重新确认，不擅自改道。
- 实施完成后，方案文档保持原样；实际偏差写进**新的**文档或代码注释，不回头篡改原方案。

---

## 4. 交付底线

- **不留半成品**：不提交 TODO / 占位 / 假实现 / 误导性的「脚手架 / MVP」。
- **不超范围**：不做用户没要求的「顺手」改动（重构、加校验、加遥测等）。
- **交付前自验**：跑通改动路径，给出可复核的证据（命令 + 实际输出）。
- 破坏性操作（删除无关代码、整体重写文件、清理产物）前先确认。
- **规范自持**：结论必须落在本仓库 —— 依据写进本仓库文档或代码注释；
  需要提原型时只链接 [`docs/prototype.md`](../prototype.md)，不直接链接原型内部文件。
- **证据时效**：原型（以及本仓库历史版本）的实测数值、日志格式、参数名、验收输出
  一律**不适用**于当前重构，必须重新验证后才能写进规范；未验证的结论要显式标注「待验证」。
- **不依赖默认值**（**全局规则**）：代码里设置**任何**参数（平台 API、库、编解码器、系统服务）
  都必须**显式写出取值**，不得依赖"默认值"；拿到结果后**回读确认**实际生效值。
  协议侧**允许缺省**（上游可以不给），但缺省必须**在代码里落成显式常量或推导规则** ——
  "上游没给" ≠ "代码里也不写"。
  依据：实测已多次踩到"默认值与真值不符 / 默认值埋坑"
  （见 [`agent/encode-format.md`](agent/encode-format.md) §2）。
- 代码文件增删或移动后，同步更新 [`docs/code-map.md`](../code-map.md)。

## 5. 实施前自检清单

- [ ] 已与用户讨论过目标与方案，并列清了取舍与风险？
- [ ] 方案文档已写入 `docs/plans/`，且用户已明确批准实施？
- [ ] 本次改动未超出用户批准的范围？
- [ ] 本轮用户**没有**要求提交 → 我**没有**执行任何 git 写操作？（另见 [`git.md`](git.md)）
- [ ] 所有新增 / 修改的类、函数、结构体及其成员都有中文文档注释？（另见 [`comments.md`](comments.md)）
- [ ] 所有依据都落在本仓库（文档或代码注释），提及原型时只链接 `docs/prototype.md`？
- [ ] 没有把原型的实测数值 / 日志格式 / 验收输出当作本次的结论（未验证的已标注「待验证」）？
- [ ] 涉及 `:agent` / `:app` 的改动已对照各自模块规范（[`agent/module.md`](agent/module.md) / [`app/module.md`](app/module.md)）？
- [ ] `docs/code-map.md` 已随文件增删同步更新？
- [ ] 新增 / 改动的文档符合 [`docs.md`](docs.md)（一个文件一件事、未超 200 行 / 12 KB、已登记索引）？
- [ ] 改动路径已实跑验证，证据充分？

## 6. 查资料：**先文档，后源码**

问「某个库 / 平台 API 该怎么用」时，顺序固定：

1. **先查文档** —— 用文档查询工具（本机可用 `find-docs`：`ctx7 library <名字> "<问题>"` →
   `ctx7 docs <libraryId> "<问题>"`）取**官方文档**的用法、参数语义与示例；
2. **文档查不到 / 版本对不上 / 必须确认实现细节** ⇒ 才读源码（解包源码、上游仓库文件），
   并在结论里写清「为什么只能靠源码」。

理由：文档是**作者视角的意图**（推荐用法、参数语义、版本差异），源码是**实现细节** ——
先读源码容易把「偶然的实现」当成「约定的接口」，更慢、也更容易读错版本。

⚠️ **版本一律以实际安装的为准**：清单 / 锁文件（`Cargo.toml` + `Cargo.lock`、`build.gradle.kts`、
`package.json`）优先于文档站的最新版说明。
踩过：egui 0.36 的滚轮增量字段叫 `smooth_scroll_delta`，而记忆里的 `raw_scroll_delta`
在这个版本**根本不存在** ✗ —— 当时是翻源码才发现的，本该先查文档。
