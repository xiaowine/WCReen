## 3. 容量（**不做容量处理**）

**决定（2026-10-07）**：PC 侧**不做任何容量处理** —— 不设上限、不做准入控制、不做降级、
不踢已有路、不做预算账本 / 运行期看门狗 / 结果缓存。**容量由运行平台硬件决定**，仅此而已。

| 做 | 不做 |
|---|---|
| **硬解强校验**（§2）：拿不到硬解即**明确失败**，绝不静默软解 | 预算模型 · 准入流程 · 拒绝新增路 · 降级（改分辨率 / 帧率 / 码率）· 踢已有路 · 看门狗 · 结果缓存 |
| **实测记录**：并发上限与成本只作**事实记录** | —— |

**实测事实**（本机 RTX 4070 Laptop；完整数据见 [`spike 实测报告`](../../plans/2026-10-07-pc-spike-report.md) §5）：

- 加路**从不失败** —— 一路加到 32 路（1080p）全部成功，且**每一路都通过硬解校验**；
- 超出时表现为**每路 fps 按比例下降**（1080p：8 路 60 fps → 12 路 44 fps → 16 路 32 fps），**不是**硬失败，也没有参数被改；
- 两个分辨率（1080p / 1440×3200）独立收敛到同一吞吐 **≈ 1.0–1.1 Gpixel/s**。

⇒ **不存在「超容量」这个可判定的状态**（加路不会失败，也不触发任何边界事件）⇒ 准入控制本就无从下手，
**这是不做容量处理的直接依据。**

> **注意**：「不做容量处理」≠「容量无限」。路数越多每路 fps 越低，
> 这个后果由**上层（UI / 用户）**承担，PC 侧不代偿、不拒绝、不降级。

## 4. 输入上报：鼠标合并与限频（**已实现**）

**问题**：现代鼠标上报率很高（125–1000 Hz 常见）。若**原封不动**每条都发一条 `input` 消息 ⇒ PC 侧每条都要
**JSON 序列化 + CRC32 + socket 写**、agent 侧每条都要**解析 + 入队** ⇒ 每秒上千条消息的**协议开销是纯浪费**，
而**画面根本体现不出来**（屏刷新率才是上限）。

### 4.1 规则（**必须做**）

| 事件 | 上报方式 |
|---|---|
| **`move`** | **定频采样**：按上限频率取**最新坐标**，中间的直接丢弃 |
| **`scroll`** | **累加 `dx`/`dy`** 后按同一频率上报 —— ⚠️ **不能丢**（滚动量是**增量**语义，丢了就**少滚**） |
| **`down` / `up` / `cancel`** | **不合并、不限频、立即发**（否则点击会丢或错位） |
| **`key`** | 不合并、立即发 |

### 4.2 频率上限 = **屏刷新率**

理由：屏刷新率是"**画面能体现的上限**"，且由 PC 自己选（`applyScreen.params.refreshRate`，见
[`agent/display.md`](../agent/display.md) §2）✓ ⇒ 高于它的 `move` 对用户**没有任何可见价值**。

### 4.3 与 agent 侧的关系：**两端都要做，职责不同**

| 端 | 作用 | 机制 |
|---|---|---|
| **PC**（本节） | 省**协议开销** | 定频采样 + `scroll` 累加 |
| **agent** | **最后一道保险** | 队列合并（[`agent/input.md`](../agent/input.md) §5）⇒ PC 送多快都**不影响注入延迟** |

⚠️ 只做 agent 侧 ⇒ 每秒上千条 JSON 消息的协议开销**照付** ✗

### 4.4 实现记录（2026-10-07 实机验收通过）

实现落在 `pc/app/src/input.rs`（采样 / 键位映射，纯逻辑 + 单测）与 `ui.rs`（采集）。
**四个必须记住的决定**：① **单指模型** —— 左键 = 触点（`id=0`）、**右键 = BACK、中键 = HOME**、**Esc = BACK**；
② **滚轮符号取负**（egui 的 `smooth_scroll_delta` 与 Android 的 `AXIS_VSCROLL` **同向异号**）；
③ **失焦 / 鼠标在窗外松开必须发 `cancel` / 补 `up`**（否则 agent 侧那个触点**永远按着** ✗）；
④ 会话线程是**唯一写者**，故 [`conn::POLL_INTERVAL`](../../../pc/app/src/conn.rs)（**8ms**）就是"鼠标动了 → 消息上线路"的最坏延迟
（原 500ms 只是判活粒度 ✗）；**子系统级被拒**（`inputDenied`）后要**停掉生产端**。
细节表与实机验收数值见 [`changelog.md`](changelog.md) §1。

⚠️ **踩过的坑（必记）**：触点按下 / 抬起**绝不能挂在 `drag_started` / `drag_stopped` 上** ✗ —— egui 的判定是
「按下够久或移动够远才算拖」（原话：*鼠标按下 ≠ 正在拖动，可能只是点击的开头*），所以**纯点击一路都不触发**，
症状是「**拖动有效、点击完全没反应**」（实测踩到）。正确做法是**事件驱动**：`pointer.primary_pressed()`
**且指针在画面上** ⇒ 发 `down`；`pointer.primary_released()` **且本端正按着** ⇒ 发 `up`（抬在哪里都算）；只用主键。

## 5. 连接与 adb 转发（**已实现**）

**通道**：adb forward 或局域网直连；PC 连的是**本地端口** `127.0.0.1:27183`，不是设备本身。

**故障：转发会随 USB 断开被 adb 清掉**。`adb forward` 挂在 **adb 传输连接**上 —— USB 一掉、传输消失，
转发被 adb **一并清掉**，插回来**不会自动恢复** ⇒ 端口一直**被拒**，重连循环每秒重试但**永远失败**
（实测：`adb forward --list` 为空、端口拒连、**设备在线**）。

**自愈**（`pc/app/src/forward.rs`，新增）：**只在连接被拒**（`ErrorKind::ConnectionRefused`）时补发
`adb forward tcp:<port> localabstract:<name>`，**限频 ≥5s**；补不好则给**并列诊断**（设备离线 /
agent 没在下这个名 / 没装 adb）+ **可照抄的命令**；**转发正常时不产生任何 adb 子进程**。

CLI 新增 `--name <NAME>`（缺省 `wcreen`，与 agent 的 `--name` 同名），用于自动重建转发。

⚠️ **断开重连不保屏** —— agent 侧「断开即拆屏」是 **S2 语义**；「断开冻结 + 重连认领」属 **S5**（未做）。
