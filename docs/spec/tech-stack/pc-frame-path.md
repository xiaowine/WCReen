## 2. 多路合流、硬解与帧通路

**多路合流（多个源 → 一个客户端）**要求解码帧走 GPU，否则每路 1080p60 的 CPU 色彩转换 + RGBA
上传（≈ 500 MB/s/路）会让 CPU 与内存带宽随路数线性爆炸 —— 这就是选 egui + wgpu 的直接原因。
**不设固定的路数 / 分辨率 / 帧率上限** —— 容量由**运行平台硬件**决定，且**不做任何容量处理**（见 [`pc.md`](pc.md) §3）。

**三个环节必须分开看**：

| 环节 | 归谁做 | 说明 |
|---|---|---|
| 解码 | **硬件解码器**（D3D11VA / VideoToolbox / VAAPI / NVDEC） | 固定功能单元，CPU 开销小 |
| 色彩转换（NV12 → RGB） | **GPU 着色器** | 放在 CPU 上做才是真正贵的那部分 |
| 解码帧 → UI 纹理 | 见下方帧通路阶梯 | **硬件解码器的输出不是 wgpu 纹理**，这是唯一的难点 |

**帧通路成本阶梯**（spike 须按三档实测 CPU / 延迟 / 带宽）：

| 档 | 路径 | 代价与现状 |
|---|---|---|
| **T0 零拷贝** | hwaccel 帧经 `create_texture_from_hal` / `texture_from_raw` 包成 wgpu 纹理 | CPU ≈ 0；但平台差异大且**部分不可行**：wgpu 的 `texture_from_dmabuf_fd` **不支持多平面（NV12）dma-buf**（gfx-rs/wgpu #9801、#10059），Linux 需用裸 ash 手写导入；`create_texture_from_hal` 为 `unsafe`，历史上有崩溃 issue（#6248） |
| **T1 回读 + GPU 转换**（默认落地） | `av_hwframe_transfer_data` 回读到内存 → 上传两张平面纹理 → 着色器转 RGB | CPU 只付一次总线回读（1080p60 NV12 ≈ 190 MB/s/路），无 CPU 色彩转换 |
| **T2 软解 + CPU 转换 + RGBA 上传** | 软件解码 + swscale → CPU 侧图像 | **不做** —— PC 侧只走硬解，硬解不可用即失败（见下方联动约束） |

**⚠️ 关键实测：FFmpeg 不会因为"本机不支持"而报错，它会静默软解**

这决定「不做软解」怎么实现。实测（RTX 4070 Laptop / ffmpeg 9.0.2 / `-hwaccel d3d11va`，判据 = 解出的帧是否为硬件帧）：

| 输入 | 解出的帧 | 判定 |
|---|---|---|
| H.264 4:2:0 8-bit | `d3d11` | ✅ 真硬解 |
| H.264 4:4:4 / 10-bit | `yuv444p` / `yuv420p10le` | ❌ **静默软解，零报错** |
| HEVC Main / Main10 | `d3d11` | ✅ 真硬解 |
| HEVC 4:4:4 | `yuv444p` | ❌ **静默软解**（尽管 D3D11 profile 列表里有 `HEVC_VLD_Main444`） |
| H.264 1440x3200 | `d3d11` | ✅ 真硬解 |
| MPEG-4 **1440x3200**（D3D11 报 `configs=0`） | `yuv420p` | ❌ **静默软解，零报错** |

两条结论：① **"尺寸不支持会报错"不成立** —— 尺寸超限与 profile 不支持的行为完全一样（**静默降级**，
每条命令的退出码都是 0）⇒ **不存在"靠系统报错"这条路，报错必须由我们自己产生**；
② **OS 广告的能力 ≠ FFmpeg 会使用** —— 能力列表（profile / 像素格式 / `configs`）只能当**候选**，判据必须是实跑。

**因此「不做软解」的强制手段是：逐路、首帧校验"帧确实是硬件帧"**：

```
建解码器 → 解出首帧 → if frame->hw_frames_ctx == null（或 frame->format != AV_PIX_FMT_D3D11）
                        → 判定"该参数在本机无法硬解" + 抛出带参数的明确错误 + 回滚该路
                     else → 通过
```

校验必须**按参数逐路做**（codec / profile / 位深 / 尺寸任一变化都要重验）；**这一条不因「不做容量处理」而放宽** —— 它保证的是「绝不软解」，与容量无关。

**联动约束（硬要求）**：PC 侧**只做硬解，不做软解回退** —— 硬解不可用即**明确失败**，不悄悄降级。
因此 agent 侧编码参数被 PC 硬解能力反向约束（H.264 / HEVC、4:2:0、8-bit、常规 profile / level）；
编出 4:4:4、10-bit 或超出硬解器尺寸上限时 PC 端**直接报错**，不回落软解。

→ 由此 **能力协商由优化项升为必需项**：协议里必须有能力交换 / 协商（**必需项**），连接建立时核对编码参数
与 PC 硬解能力，含 **分辨率上限**（手机原生 1440x3200 这类纵向超长尺寸可能超出硬解器 max，须实测）。
**方向、决定权、消息序列与字段留到协议设计阶段定**，本文件只锁约束：协商结果必须保证接收端能硬解，做不到就**明确失败**。
见 [`tech-stack/overview.md`](overview.md) §5 未决项 7。

**一个硬耦合（决定协商能谈什么）**：零拷贝决定了 **编码尺寸 = 虚拟屏尺寸**（虚拟屏输出面就是编码器输入面，中间没有缩放环节）。
所以「PC 要求降分辨率」实际是让 agent **改虚拟屏尺寸**，屏内 App 看到的屏幕也随之变小；
多路合流下的「显示变小」应在 **PC 渲染侧缩放**（解码仍用原生尺寸），只有**超出硬解器上限**时才降编码尺寸。

**延迟**：硬解器有帧池深度，需低延迟标志（如 `AV_CODEC_FLAG_LOW_DELAY`）与受限的 async depth。
**已量化**（spike 实测，见[报告](../../plans/2026-10-07-pc-spike-report.md) §4）：播放侧延迟 **≈ 缓冲帧数 × 帧间隔**
（实测斜率 16.8 ms/帧 @60fps），回读 + 上传的固定成本只有 **~5 ms @1080p** ⇒ **延迟由缓冲深度主导**。

**本应用是远程操控（人要看着画面操作手机）⇒ 延迟优先 ⇒ 缓冲取尽可能小**：

| 项 | 结论 |
|---|---|
| 取向 | **最小缓冲**，不为抗抖动留余量 |
| 实测下限 | **2 帧 = 38.6 ms**（本机 1080p60）—— 通道与展示队列各至少 1 帧 |
| 对比 | 6 帧 = 105 ms ⇒ 最小缓冲省 **66 ms** |
| 代价 | 缓冲越浅，抖动越容易打穿 ⇒ 打穿后按丢帧重对齐（不是降级） |

**但真实链路是「直播语义」，缓冲的角色会变**（spike 实测，报告 §3b）：

- 真实链路送的是**裸 Annex-B 码流**，**完全没有 PTS** ✗ ⇒ 没有可对齐的"源时间轴" ⇒ PC **不做时间轴节流，到达即上屏** ✓。
- 此时 `lat` = **流水线成本本身（实测 9.2 ms）**，**不再由缓冲深度主导**；缓冲退化为**抖动吸收器** ⇒
  应当**按预期网络抖动来定**，而不是按延迟预算反推。
- ⚠️ **不得从裸解复用器推导帧率**：FFmpeg 对裸流猜出 `r_frame_rate=120/1`、`avg_frame_rate=25/1`（真实 60）✗ 必须用握手协商来的参数。
- ✅ 裸流**中途切入可用**（每个 IDR 自带参数集）⇒ 接入不必等关键帧之前的字节。
