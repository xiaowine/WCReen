# 技术栈变更记录 · 归档（2026-10-06）

> 本文件是 [`tech-stack/changelog.md`](changelog.md) 的**归档部分**（2026-10-06 追加系列，初版–追加 11）。
> **当前变更记录以 [`tech-stack/changelog.md`](changelog.md) 为准**，本文件只记历史。

---

- **2026-10-06 初版**：确立三侧技术栈（`:agent` Kotlin/JVM、`:app` Kotlin/JVM 留空、PC Rust + GPUI + FFmpeg）；
  协议先定传输无关性；依赖按需尽量少；引入 JVM 纯逻辑单测。
  PC 端被否方案见 §1。
- **2026-10-06 追加**：PC 端目标定为**跨平台**（Windows / macOS / Linux）；
  FFmpeg 接入定为**动态链接共享库 + 随包分发**（否掉构建期自建/静态链接、纯 Rust 解码、sidecar）；
  GPUI 依赖锁定策略定为「spike 中 crates.io `0.2.2` 与 git 主干各跑一次」；
  记录 GPUI 后端矩阵与三项风险（pre-1.0 分叉、视频帧上屏为 CPU BGRA 无零拷贝通路、硬解三平台各一套）。
- **2026-10-06 追加 2**：PC 端形态追加**多路合流**（多个源 → 一个客户端）。
  实查 GPUI 源码后细化「视频帧上屏」风险：`SurfaceSource` 仅 `CVPixelBuffer` 且 API 在非 Apple 平台被 `cfg` 掉、
  主干 `gpui_wgpu` 的 wgpu 后端是内部实现、发布版 0.2.2 公开 API 无自定义着色器入口。
  由此把 UI 层收敛为 **A（GPUI 主干 + 自研 wgpu 纹理入口，需维护 patch）** 与
  **B（egui + wgpu，用 `register_native_texture`）** 二选一；排除「发布版 GPUI + CPU 上传」。
- **2026-10-06 追加 3**：UI 层**定为 B：egui + wgpu**。依据：egui 有官方的外部 wgpu 纹理入口
  （`register_native_texture` / `egui_wgpu::Callback`）、自带控件集、版本与生态稳定；
  GPUI 因「无跨平台视频纹理入口 + 与主干分叉 + 不含控件库」被否决（依据见 §1）。
  渲染后端随之统一为 wgpu（macOS Metal / Windows D3D12 / Linux Vulkan）。
  同步记录「多路合流」对解码帧必须走 GPU 纹理的硬要求。
- **2026-10-06 追加 4**：明确区分「解码在 GPU」「色彩转换」「解码帧 → UI 纹理」三个环节，
  并给出帧通路成本阶梯 **T0 零拷贝 / T1 回读 + GPU 转换（默认）/ T2 软解 + CPU 转换（排除）**。
  记录 T0 的平台障碍：wgpu `texture_from_dmabuf_fd` 不支持多平面 NV12 dma-buf（#9801、#10059），
  `create_texture_from_hal` 为 unsafe 且有崩溃记录（#6248）。
  新增未决项：**编码参数与硬解可达性**（agent 侧须按 PC 硬解能力定参，并做能力协商 / 软解回退）。
- **2026-10-06 追加 5**：**PC 侧不做软解**，去掉软解回退需求（T2 由「性能不可接受」升级为「明确不做」）。
  硬解不可用即明确失败并给出可诊断错误；由此**能力协商由优化项升为必需项**，
  且 agent 侧编码参数被 PC 硬解能力反向约束（含分辨率上限）。
- **2026-10-06 追加 6**：能力协商的**方向不写死**（PC → agent / agent → PC / 双向都可），
  倾向「**PC 决策 + agent 可行性否决**」，最终参数以 agent 确认为准（新增未决项 7）。
  同时记录硬耦合：零拷贝下 **编码尺寸 = 虚拟屏尺寸**，降编码尺寸会改变屏内 App 看到的屏幕尺寸；
  多路缩放在 PC 渲染侧做，仅当**超出硬解器上限**时才降编码尺寸。
- **2026-10-06 追加 7**：确认「协商必需、细节后定」—— 能力协商保留为**必需项**，
  但**方向 / 决定权 / 消息序列 / 字段全部移到协议设计阶段**（未决项 7 → 只锁「协商结果必须保证接收端能硬解，否则明确失败」；
  协商消息归入未决项 8「协议格式」）。
- **2026-10-06 追加 8**：**取消固定容量上限**（不设目标路数 / 单路分辨率 / 帧率），
  容量改为**运行时由平台硬件决定**：新增 §1「容量模型」小节（静态探测可查询项 + 运行时自适应不可查询项 +
  降级顺序：先降分辨率/帧率 → 再降路数 → 一律明确告知，**绝不软解**），并强调「动态 ≠ 无限制，必须配预算模型与拒绝策略」。
  未决项 4 / 5 随之改写。
- **2026-10-06 追加 9**：细化「静态探测」的**可靠性分级** —— 区分
  ① 可靠可查（硬解设备、codec↔hw 映射、wgpu adapter 限制）、
  ② **名义可查但不可靠**（`AVHWFramesConstraints` / `CheckVideoDecoderFormat` 在 D3D11VA 上常返回规范范围而非设备能力）、
  ③ 查不到只能试错（并发会话上限、显存余量、缓冲深度、零拷贝互操作可行性、长跑稳定性等）。
  定规则：**探测给候选，试错给结论**；缓存实测结果而非探测结果（实现细节见 spike 方案 §3.3）。
- **2026-10-06 追加 10**：实测发现 **FFmpeg 对不支持的参数会静默软解且退出码为 0**
  （H.264 4:4:4 / 10-bit、HEVC 4:4:4、MPEG-4 @1440x3200 均为静默软解；尺寸超限与 profile 不支持行为一致）。
  由此定死「不做软解」的**唯一强制手段**：**逐路首帧校验帧是硬件帧**
  （`hw_frames_ctx != null` / `format == AV_PIX_FMT_D3D11`），报错由我们自己产生；
  并明确 **OS 广告的能力列表只能当候选，判据必须实跑**。同批实测还确认：
  wgpu(DX12) 与 D3D11 解码设备 **LUID 一致**（跨适配器不是阻塞），
  wgpu 30 支持 `TEXTURE_FORMAT_NV12` 与 R8/Rg8/R16/Rg16 平面格式。
- **2026-10-06 追加 11**：**删除容量模型的「降级机制」**（原「先降分辨率 / 帧率 → 再降路数」）——
  改为：**超出容量时不做任何降级**，由**准入控制**处理（**拒绝新增路**，不踢已有路、不改已有路参数），
  拒绝须明确告知、绝不软解。连带更新：未决项 4 改为「探测项与**准入控制**」；
  spike 方案验收 7、运行期看门狗与故障注入开关的描述同步（看门狗改为**直接回收该路**）。
  触发原因：agent 侧运行期**没有可原地改的参数**（见 [`agent/display.md`](../agent/display.md) §2.1），
  原降级顺序与 agent 实测矛盾。
